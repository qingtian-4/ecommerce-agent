# 电商客服 Agent 项目：开源项目 / 数据集 / 评测 调研报告

> 调研时间：2026-10 · 目标：确定「从零开始」还是「基于开源改造」，并明确数据与评测的获取路径。

---

## 一、结论速览（TL;DR）

| 问题 | 结论 |
|---|---|
| 有合适的开源项目可以改吗？ | **有，但没有一个能直接用。** 3~5 个项目值得抄架构，没有一个提供可复用的业务数据 + 评测集 |
| 从零开始还是改开源？ | **建议：借鉴架构 + 从零搭建自己的骨架。** 直接 fork 大而全的项目（依赖 MySQL/Redis/Nacos/Qdrant/OpenSearch）会把你拖进运维泥潭，而不是 RAG |
| 电商客服数据有现成的吗？ | **中文真实客服语料有（JDDC 等），但几乎都是"对话文本"**，用来做 SFT / 意图分类，**不能直接评测带工具调用的 Agent** |
| 评测需要自己做吗？ | **必须自己做。** 这是项目最大的护城河，也是小红书那份建议的核心（"没有评测的优化，很难证明设计是有效的"） |
| 有现成评测框架吗？ | **有且权威**：`ECom-Bench`（电商客服专用，Apache-2.0）、`τ²-bench`（通用工具调用 Agent，MIT），可直接作为外部对标 |
| 第一步做什么？ | **先造业务数据和 Baseline，不写 Agent。** 详见第五节 |

## 二、GitHub 开源项目盘点

### 2.1 第一梯队：架构值得抄（推荐精读）

#### ① XiaoduoAILab/ECom-Bench ⭐30 — 最权威，但它不是"客服系统"，是"评测基准"

- **性质**：上海交大 + 晓多 AI Lab，EMNLP 2025 Industry Track 论文官方开源
- **技术**：LangGraph + MCP + LangChain，基于 `sierra-research/tau-bench` 二次开发
- **它给了什么**（全文最有价值的部分）：
  - **53 条人工校验任务**（其中 18 条含多模态识图）
  - **21 类 MCP 工具**（商品查询、订单修改、退换货…部分工具要求严格调用顺序）
  - **模拟数据库**（商品 / 物流 / 订单 / 发票 JSON）
  - **用户 persona 模拟器**（消费者类型 + 情绪 / 细心度 / 耐心 / 信任 / 维权意识）
  - **规则化评测器**：三维度打分 —— Action（数据库最终状态 vs 期望状态）、Search（是否调用了必需检索工具）、Output（关键词是否命中）
  - **pass^k 指标**（同一任务跑 k 次全部成功的概率）
- **对标分数**：GPT-4o 仅 pass^1=44.03 / pass^3=16.98，pass^8 掉到 7.55%
- **⚠️ 注意**：它定位是**评测框架**，官方明确声明"包含模拟用户数据，仅用于非生产测试"。你要做的是**能跑的系统**，需要把它的 env / 工具 / 数据库设计思路搬过来，但服务端自己写
- 🔗 https://github.com/XiaoduoAILab/ECom-Bench · 论文 https://arxiv.org/abs/2507.05639

#### ② iwcdoit/enterprise-customer-service-agent-v2 ⭐38 — 工程治理最完整

**如果目标是"简历能讲工程思维"，这个项目的设计几乎逐条命中了小红书建议里最难的部分。**

已实现且值得抄的：

- 混合检索：向量 + BM25 + **RRF 融合** + 可选 Reranker
- **知识文档生命周期**：版本 / 生效时间 / 内容哈希 / 双索引管理（← 很少见，业务真实感强）
- **有界任务规划** + ReAct 执行 + LangGraph Checkpoint 持久化
- **Tool Registry + Business Gateway**：读写工具分级治理、调用上下文签名、**Approval Token**、幂等保护
- 人工队列 + 坐席接管 + **Agent 恢复**
- 租户级模型 / 检索策略、缓存策略、**Token 预算控制**
- Prometheus + OpenTelemetry + LangSmith

**代价**：MySQL + Redis + Qdrant/Milvus + OpenSearch 四件套，本地跑起来成本高。**建议只读它的 `tools/` 和 `workflows/` 目录，抄权限与幂等设计，不要整体 fork。**
🔗 https://github.com/iwcdoit/enterprise-customer-service-agent-v2

#### ③ whichmen/dxl-commerce-agent ⭐127 — 最"实战"，有真实平台接入 + 离线 Eval

- **亮点**：不是玩具。接了淘宝千牛 / 拼多多 / 抖音飞鸽 / 快手小店 / 小红书千帆 / 视频号小店 六个平台的真实消息
- **技术**：OpenClaw + 原生 Function Calling，**13 个业务工具**走带鉴权的 HTTP Tool Gateway，SQLite 存会话与决策
- **安全边界**：分离 API Key、工具权限开关、退款后端二次校验、`manual` 人工接管
- **Eval**：**72 项自动化测试 + 50 条确定性离线 Eval** + CI + Secret Scan
- **启示**：证明了「Agent 不猜业务事实，事实一律走工具」这条红线怎么落地
- ⚠️ 平台接入依赖 Cookie / Appium / 浏览器 Profile，**法务与稳定性风险高，简历项目不建议碰**
- 🔗 https://github.com/whichmen/dxl-commerce-agent

#### ④ WangWeiqiang-UCAS/E-commerce-Smart-Agent ⭐141 — 最接近"标准答案"

- **技术栈**：LangChain/LangGraph + FastAPI + SQLModel + Celery + **PostgreSQL/pgvector** + Redis + Gradio + WebSocket
- **命中需求的点**：意图路由 → 订单查询工具 / 退货资格校验 → **高风险退款转人工审核队列** → 管理员工作台（任务队列、会话回放、一键决策）→ Celery 异步执行退款与短信
- **结构清晰**：`app/graph/{nodes,state,tools,workflow}.py` 分层规范，是很好的骨架参考
- ⚠️ 偏"人机协作工作流"，RAG 部分较薄（只加载 policy.md 做 embedding）
- 🔗 https://github.com/WangWeiqiang-UCAS/E-commerce-Smart-Agent

- **[Morizeyao/EComAgentBench_](https://github.com/Morizeyao/EComAgentBench_)**（EMNLP 2026 Industry Track，Shopee）：**662 条验证样本 + 6,645 条 rubric**。任务设计很硬核 —— 用户需求被**故意分散在三个信息源**（可见 query / 工具才能拿到的 persona / 脚本化追问），考的是 Agent 主动澄清需求的能力。评测用 **rubric-based LLM-as-Judge + exact-match**。产品库 25GB 需从 HF 单独下载。**英文 + 单一市场 + 电子产品，不适合直接当你的中文客服评测，但 rubric 设计方法必须抄**

### 2.4 选型建议

```
不要 fork 任何一个完整项目。
做法：新建空仓库 →
  骨架分层     参考 WangWeiqiang-UCAS/E-commerce-Smart-Agent 的 graph 分层
  工具与权限   参考 iwcdoit/enterprise-customer-service-agent-v2
  评测与护栏   参考 moondream69/Multi-Agent-E-commerce-System
  检索与指标   参考 SR88888888/zhiwei-ecommerce-cs-agent
  外部对标     对齐 XiaoduoAILab/ECom-Bench
```

**判断一个仓库能不能抄的三个硬标准**（star 数不算标准）：

1. 有没有**评测代码**（`evals/`、`benchmark/`、可跑的指标脚本）—— 没有的一律按"README 驱动开发"处理
2. **工具层是否独立成模块**（有 Tool Registry / schema / 鉴权），还是把工具逻辑硬编码在 prompt 里
3. **License**（MIT / Apache-2.0 可商用，AGPL 慎用）+ 最近 3 个月是否有提交

## 三、数据：到底有没有现成的？

### 3.1 关键认知：你需要三种完全不同的数据

很多人卡在这里，是因为把三件事混成一件。**没有任何一个公开数据集能同时给你这三样。**

| 层级 | 是什么 | 有现成的吗 |
|---|---|---|
| **L1 知识文档** | 退换货政策、配送说明、FAQ、商品手册 | ⚠️ 半现成。可自己写，也可从公开商品页 / 政策页整理。**最没技术含量但最必须** |
| **L2 业务数据库** | 订单、物流、库存、用户、退款单（mock） | ❌ 基本没有。必须自己造（结构化业务数据） |
| **L3 评测黄金集** | 问题 → 期望答案 + 期望调用的工具 + 期望命中的文档 | ❌ **必须自己做，这是项目核心资产** |
| （附带）真实对话语料 | 用于 SFT / 意图分类 / persona 设计 | ✅ 有，见下表 |

### 3.2 可用的公开数据

| 数据集 | 规模 | 获取 | 适合用途 | 不适合 |
|---|---|---|---|---|
| **JDDC**（京东对话挑战赛，LREC 2020） | ~29 万会话 | 需向京东申请授权；GitHub 上有第三方格式转换（[zhangbo2008/JDDC_for_train_gpt_data](https://github.com/zhangbo2008/JDDC_for_train_gpt_data)、[dasiki/Dialog-System-with-Task-Retrieval-and-Seq2seq](https://github.com/dasiki/Dialog-System-with-Task-Retrieval-and-Seq2seq)） | 抽真实问题、理解真实客服话术、做 **persona 设计** | 评测 Agent（无工具调用、无业务库、无 ground truth 状态） |
| **JDDC 2.1** | 更大，含多模态 | [hrlinlp/jddc2.1](https://github.com/hrlinlp/jddc2.1)，同样需申请 | 同上 | 同上 |
| **ECom-Bench 数据** | 53 任务 / 21 工具 / 模拟 DB / persona | [GitHub](https://github.com/XiaoduoAILab/ECom-Bench) 直接开源 | **抄它的任务设计、工具 schema、DB 结构** | 直接当自己的业务库（家电家具域，模拟数据） |
| **EComAgentBench** | 662 任务 / 6,645 rubric | `benchmark.jsonl` 开源；`product.db` 25GB 从 HF 下 | **抄 rubric 设计方法** | 英文、电子产品、单一市场 |
| **CCSE-CS** | 中文客服共情对话 | [haimianxing/CCSE-CS-Empathetic-Culture-AI](https://github.com/haimianxing/CCSE-CS-Empathetic-Culture-AI) | 情绪 / 共情维度参考 | Agent 能力评测 |
| **ShopBot-SFT-Dataset** | 电商客服对话 SFT/RLHF | [RyanMeg123/ShopBot-SFT-Dataset](https://github.com/RyanMeg123/ShopBot-SFT-Dataset) | SFT 素材 | 评测 |

**结论：L1/L2 可以造 + 借鉴，L3 只能自己做。真实对话语料（JDDC）的真正价值是"让我的测试问题看起来像真人问的"，而不是当评测集。**

### 3.3 实战建议：数据怎么造

**L1 知识文档（1~2 天）**

- 选 1 个具体品类（**别做全品类，这是最容易犯的错**）。建议：数码配件 或 小家电
- 造 15~25 篇文档：退换货政策、发货时效、发票规则、价保规则、安装服务、常见故障排查、5~8 个商品详情页
- **故意埋坑**：互相冲突的条款（不同品类退货期不同）、需要多跳才能回答的规则（"价保"要先查订单时间再查活动规则）、有生效时间的旧政策（考知识版本管理）
- 存成 Markdown，带 front-matter 元数据（版本 / 生效日期 / 适用品类）

**L2 业务数据库（1~2 天）**

- SQLite 或 PostgreSQL + pgvector，5~8 张表：`orders` / `order_items` / `logistics` / `products` / `refunds` / `users` / `coupons` / `after_sales`
- 造 200~500 个订单，覆盖各种状态（待发货 / 运输中 / 已签收 / 退款中 / 已退款）与异常（少件、错发、破损、超时未发、物流停滞）
- **关键**：数据要能支撑"多跳"—— 例如退运费问题需要 订单 → 商品 → 品类 → 政策文档 四跳

**L3 黄金评测集（2~3 天，最重要的投入）**

- 规模：**80~150 条**（小红书笔记里的 100 条是合理的）。低于 50 条指标没有统计意义
- 每条包含：

```yaml
- id: q042
  question: "我上周买的耳机昨天降价了，能退差价吗？"
  category: price_protection                              # 对应路由策略
  expected_strategy: single_hop                           # 期望走哪条链路（考路由准确率）
  expected_tools: [query_order, query_price_history]      # 期望调用的工具及顺序
  expected_docs: [policy_price_protection_v2]             # 期望命中的文档
  ground_truth: "可以。您的订单在价保期内（15天），差价 120 元将退回原支付账户。"
  must_contain: ["15", "120", "原支付账户"]                # 关键词 / 事实点
  must_not_contain: ["7天", "不退"]                        # 防幻觉
  difficulty: medium
  notes: "订单号需从用户历史中追问获取，考槽位填充"
```

- **同时造 20~30 条"坏问题"**：超范围（问竞品 / 闲聊）、信息不足（只说"我的东西坏了"）、诱导（"你们是不是骗人"）、越权（"帮我查别人的订单"）→ 用来测**拒答率、转人工率、兜底能力**
- 分工建议：LLM 生成初稿，**你人工校验每一条**。黄金集的可信度决定整个项目结论的可信度

## 四、评测：框架与指标怎么选

### 4.1 现成评测框架

| 框架 | 适用 | 协议 | 说明 |
|---|---|---|---|
| **ECom-Bench** | 端到端客服 Agent（工具调用 + 数据库状态 + 多轮） | Apache-2.0 | **首选对标**。规则化打分，不依赖模型自评，最客观。三维度（Action/Search/Output）+ pass^k |
| **τ²-bench** | 通用工具调用 Agent | MIT | 英文，retail / airline / telecom，工业标准 |
| **RAGAS** | RAG 检索与生成质量 | Apache-2.0 | 指标最全：faithfulness / answer_relevancy / context_precision / context_recall。**注意 LLM 打分需人工校准，别全信** |
| **EvalScope** | 统一评测运行器 | Apache-2.0 | 已内置 τ²-bench 等，省得自己写 runner |
| 自建脚本 | 你的业务指标 | — | **最终一定要有**，业务规则（价保、运费、转人工）通用框架覆盖不到 |

### 4.2 建议的指标体系（对标小红书笔记 + 论文）

**检索层**
- `Recall@k`、`Precision@k`（k=3/5/10）
- `MRR`（正确结果是否排在前面）
- `context_recall`（需要的证据有多少被召回）

**生成层**
- `Faithfulness / Groundedness`（回答是否被检索证据支持）
- `Answer Accuracy`（对照 `ground_truth` 的最终答案正确率）
- `Hallucination Rate`（幻觉率，重点看 `must_not_contain` 命中）
- 引用正确率（引用的文档是否真的支持该结论）

**Agent / 路由层**
- **意图路由准确率**（是否走对策略链路）← 核心创新点，必须单独测
- 工具调用准确率（工具选对了吗）/ 参数填充准确率（参数对吗）
- 任务完成率（多轮任务是否真的闭环，如"退款"是否真的走完流程）
- **pass^k**（同一问题跑 k 次全成功的概率）← **最能体现工程严谨性，强烈建议做**
- 拒答率 / 转人工率（在应该拒答的样本上）

**工程层**
- P50 / P95 延迟（**分链路统计**，别只看平均）
- Token 消耗与单次成本（人民币）
- 各阶段耗时占比（路由 / 检索 / 重排 / 生成 / 工具）

### 4.3 三个必须遵守的评测纪律

1. **先有 Baseline，再谈优化。** 顺序必须是：Basic RAG Baseline → 打一次分 → 加混合检索 → 再打一次 → 加 RRF → 再打一次……**每一步单独记录对效果和成本的影响**。这正是笔记里"我做了这个改动，具体提升了多少？"的答案
2. **固定评测环境。** 同一批问题、同一套参数、`temperature` 固定、同一版本的知识库，否则数字不可比
3. **警惕过拟合。** 黄金集调参调多了就失去意义。建议拆成 **dev（80 条调优）+ test（40 条只在最后跑）**

### 4.4 对小红书笔记里那组数字的提醒

笔记给的 `Precision 58%→85%` / `Recall 63%→91%` / `Faithfulness 54%→88%` / `幻觉率下降 62%` / `意图路由 97%` 是很好的**目标模板**，但要注意：

- **100 条样本的指标置信区间很宽。** 97% 准确率在 100 条上的 95% 置信区间约为 [91.5%, 99.4%]。面试被追问"这个提升显著吗"时，要能答上来
- 建议**自己算一遍**每个指标的 95% CI，或对每个指标跑 3 次取均值 ± 标准差。这个细节能让你在面试里明显高出一档
- 记录**指标来源**：规则判定的、LLM 判的、还是人工标的？三者可信度不同，混在一起汇报会被抓

## 五、第一步具体怎么做（4 周路线）

> **核心原则：先有数据和 Baseline，再写 Agent。** 反过来做（先搭 LangGraph 骨架，最后补数据）会导致 Agent 无处可测，最后退化成"能跑通的 Demo"。

### Week 0（1~2 天）：定范围 —— 不做这一步，后面全崩

产出 `docs/01-范围定义.md`，必须写死：

- **品类**：1 个（如"无线耳机 + 充电配件"）
- **业务范围**：售前咨询 / 订单查询 / 物流追踪 / 退换货 / 价保 / 发票 —— **挑 4~5 个，不要全要**
- **明确不做的**：复杂多商品比价、真实支付、多语言、真实平台接入
- **路由策略表**（先画表格，不写代码）：

  | 问题类型 | 处理链路 | 目标延迟 | 目标成本 |
  |---|---|---|---|
  | 简单 FAQ | 普通 RAG 单跳 | < 2s | 最低 |
  | 单跳事实问题 | 混合检索 + Rerank | < 3s | 低 |
  | 多跳问题 | 任务拆解 + 多轮检索 | < 8s | 中 |
  | 需查业务数据 | Agentic RAG（工具调用） | < 5s | 中 |
  | 证据不足 | Self-RAG 重试 → 抽取式兜底 | — | — |
  | 超范围 / 越权 | 拒答 或 转人工 | — | — |

### Week 1：数据 + 裸检索（**不碰 LLM Agent**）

1. `git init`，建目录：`data/{docs,db,eval}` / `src/{ingest,retrieval,agent,eval}` / `docs`
2. 造 L1 知识文档（15~25 篇带元数据的 Markdown）
3. 造 L2 业务库（SQLite，200~500 订单 + 异常态）
4. 造 L3 黄金集初版（**先 50 条，够跑通就行**）
5. 实现**最小检索**：切分 → 向量化（BGE-small-zh 或 bge-m3）→ Chroma/FAISS 检索
6. **立刻跑一次评测，拿到 Baseline 数字。** 此时数字大概率很难看（Precision 50% 上下），这是正常且必要的

### Week 2：检索增强（笔记里的第 2 层）

- 加 BM25（`rank_bm25` 或 SQLite FTS5）→ RRF 融合 → BGE-Reranker 重排
- 对比实验：`向量` / `BM25` / `混合` / `混合+RRF` / `混合+RRF+Rerank`，**每种都记录 Precision / Recall / MRR / 延迟**
- 加 Query Rewrite（多轮指代消解 + 口语化改写）
- 加引用溯源（回答里 `[1]` 可点开看原文片段）和"无答案拒答"

### Week 3：自适应路由 + Agentic（笔记里的第 3 层，核心创新）

- 实现**意图识别 + 复杂度路由**（建议：规则优先 + LLM 兜底，别一上来全靠 LLM）
- 按路由表接上不同链路；实现 Self-RAG（证据充分性判断 + 重试）
- 实现工具层（**独立模块 + JSON Schema + 参数校验 + 权限分级**）：`query_order` / `query_logistics` / `query_refund_status` / `check_return_eligibility` / `submit_return_request`（写操作要二次确认 + 幂等）
- 实现拒答与转人工兜底
- **再跑一次评测，重点看路由准确率**

### Week 4：评测体系 + 可观测性 + 收尾

- 补全黄金集到 100~150 条；拆 dev / test
- 实现指标脚本：规则指标 + RAGAS（faithfulness / context_recall）+ LLM judge（rubric 打分）+ pass^k
- 加可观测性：每次请求记录 路由策略 / 检索到的文档与 chunk / 每个结果的分值与排名 / 是否重试 / 调用了哪些工具 / 各阶段耗时与 token / 是否触发拒答或自纠错 → 落到 JSON 或 Langfuse
- 跑一遍 **ECom-Bench** 做外部对标（哪怕只有几条任务，也是简历亮点）
- 写 README：**架构图 + 每一步优化前后的指标对照表 + 成本与延迟表 + 已知局限**

### 面试时的讲法（笔记的核心洞察）

每个设计点都要能回答"**我做了这个改动，具体提升了多少？**"

- 不要讲"我用了 Milvus" → 要讲"数据量只有 8000 chunk，实测 FAISS 与 Milvus 召回一致，但 Milvus 让 P95 延迟多了 40ms 且增加运维成本，所以选 FAISS"
- 不要讲"我用了 Adaptive-RAG" → 要讲"我发现 62% 的问题单跳就能解决，强行上 Agent 让 P95 延迟从 1.8s 涨到 6.4s 而准确率只涨 2%，所以我做了复杂度路由，只对 38% 的复杂问题启用多轮检索"
