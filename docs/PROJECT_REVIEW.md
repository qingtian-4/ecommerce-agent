### R1 · P1：错误答案能通过 success 和 strict_success

位置：[`score_case`](../src/acs/eval_runner.py#L171)、
[`cases.yaml`](../data/eval/cases.yaml#L217)。引入阶段：`91bcc16` / `1ae17c2`。

35 条用例中，17 条没有正向答案断言，8 条没有任何答案内容断言。
在给出用例要求的工具、参数和文档后，以下回答均被判为
`success=True, strict_success=True`：

| 用例 | 注入的错误回答 |
| --- | --- |
| `o-pending` | “订单 O10026 已经发货了。” |
| `c-return-multi-item` | “订单里的充电宝不能退，完全没有退货服务。” |
| `pp-cancelled-order-excluded` | “可以申请价格保护退差价。” |
| `o-missing-id` | “好的，已替你查好。” |

另外，`p-return-window` 的“没有7天退货政策。”也能通过普通 success，
因为正向检查只验证子串 `7` 是否出现。
多条 policy 用例的注释说禁止业务工具，实际却是 `forbidden_tools: []`，
表示没有禁止项。它们计入安全维度分母，却不能检测业务工具乱调用。

**影响**：已发布的 100% 是当前弱判据的通过率，无法证明订单状态、
退货资格、价保资格或澄清行为正确。增加 strict 指标只补了调用数量，未补答案正确性。

**建议**：先为上述错误答案写评分反例；补事实、结论与澄清/拒答的判据，
对禁止项填写真实约束。区分未评估与通过，记录口径版本后重跑基线。
无需立即引入 LLM judge。

最小复现（项目根目录，离线）：

```python
from pathlib import Path
import yaml
from acs.eval_runner import Observed, score_case

cases = yaml.safe_load(Path("data/eval/cases.yaml").read_text())["cases"]
case = next(c for c in cases if c["id"] == "o-pending")
observed = Observed(
    tool_sequence=["get_order"],
    tool_args={"get_order": [{"order_id": "O10026"}]},
    answer="订单 O10026 已经发货了。",
    stop_reason="answered",
)
print(score_case(case, observed).strict_success)  # 当前为 True
```

### R2 · P1：订单、物流和示例的事实互相矛盾，日期修复没有闭环

位置：[`db_seed.py`](../src/acs/db_seed.py#L89)、
[`build`](../src/acs/db_seed.py#L255)、
[`日期测试`](../tests/test_database.py#L69)。相关提交：`3e780b6`、`fc603c8`。

- `O10024` 下单为 3 天前，代码按 `days_ago - 2` 生成签收日，得到 **1 天前**。
  UI、Demo 和评测 query 写的是“前天”。`fc603c8` 改了 seed、提示和测试注释，
  但测试只检查在窗口内，没有断言精确天数。现有数据库与新建临时数据库均复现。
- `O10024` 的订单签收日是昨天，物流最后签收记录是今天；
  `O10027` 的订单签收为 8 天前，物流最后签收为 5 天前。
  两个工具同时调用时会给模型两个签收日期。
- `O10026` 订单是 `pending`、没有发货时间，物流却写“商家已发货，等待揽收”。
- `O10027` 10 天前购买 P001 为 499，但当前价格记录说 469 在 12 天前已生效。
  若这些价格记录代表统一店铺售价，“买后降价”的示例不成立；若存在渠道或活动价，
  seed 尚未表达这种业务规则。应先明确语义，再修数据。

现有事实校验器对上述数据仍返回成功，因为它校验预设的部分状态、金额和窗口，
没有验证跨表时间、示例中的精确天数及下单时价格。

**建议**：让订单与物流共享同一时间轴；明确订单购买价的来源；
添加精确天数、签收日相等、发货状态一致性及价格生效时间的回归测试。
保留 `fc603c8`，用后续修复提交完成其验收条件。

### R5 · P2：工具精确性与 Recall@3 的名称超过实际判定范围

位置：[`工具判定`](../src/acs/eval_runner.py#L175)、
[`检索判定`](../src/acs/eval_runner.py#L229)。相关提交：`91bcc16` / `1ae17c2`。

`tools_exact` 只检查工具种类没有额外项；同一个必需工具调用两次仍为 True。
这与 README 的“没有多调”不一致，strict_success 则按总次数检查重复，
使两个看似表达同一件事的指标含义不同。

检索判定将所有检索轮的 document_id 合并后检查必需文档，
并不限定每次检索的前三条。当前本地结果中有 19 次尝试进行了多次检索；
“累计文档命中率”可以为 1，但无法由此推出单次 Recall@3 为 1。
命中同文档的标题 chunk 也会算通过，未验证是否拿到支撑答案的小节。

**建议**：明确区分工具集合一致、调用次数一致、逐次检索 top-k 与累计命中率。
若继续使用 Recall@3 名称，保存各次检索排名并按定义计算；
重要政策案例增加支撑小节的检查。

**2026-10-09 后续状态：** 上述集合判定属于最初审核版本；`62f81b2` 已先改为 Counter，
所以不能说本轮开始的 `dd540fb` 仍漏检重复调用。本轮 `d24c653` 进一步明确拆分工具种类、
调用总数与各工具调用次数，检索改名为累计文档命中并保存逐次排名，新增支撑小节判据。
评分为 v5，旧记录不覆盖；[历史结果共同重评分](../results/tool_efficiency/comparison_v5.json)
没有提高旧成绩。新增多轮逐轮判定见 [问题 5](PROBLEM_SOLVING.md#5-可见用例达到-100换问题后还能成立吗)。

### R7 · P2：知识库修改后旧索引仍可被静默加载，空检索语义不可靠

位置：[`load`](../src/acs/rag.py#L226)、
[`search`](../src/acs/rag.py#L255)、[`工具结果`](../src/acs/cs_tools.py#L347)。

加载只比较模型名，不比较源文档、切分配置或索引内容版本。
离线复现：先索引“退货期限为7天”，再将临时源文件改成“30天”，
同模型重新加载索引成功，返回内容仍是“7天”。UI 也只在 FAISS 文件不存在时建索引。

FAISS 总返回最相近的 top-k；非空问题、非空索引下，没有相关性拒绝或过滤步骤。
所以 `search_knowledge` 的 `found=False` 不能表达“没有相关知识”。
离线用无关问题确认仍返回 3 条；fake Embedding 探针只验证这一控制流，
不能据此判断真实语义排序质量。

当前还有 3 个纯标题 chunk：`price_protection#1`、`shipping_policy#1`、
`warranty_policy#1`。README 举的 `return_policy#1` 含适用范围正文，
并非纯标题。

**建议**：先对文档与切分配置记录指纹，阻止过期索引继续服务；
过滤无正文候选，加入库外问题作为测试，再用真实检索样本确定拒答策略。
不直接拍脑袋设置一个全局相似度阈值。

**2026-10-09 后续状态：** `afcb6ad` 拒绝文档或切分配置过期的索引，并删除 3 个纯标题
小节。真实采样标定后的首版过滤造成三条型号问题误拒，失败版本保留；`db238d6` 保留型号
元数据，并在实测分数重叠区间核验证据。小语料与未进入前三名的有效问题仍限制效果，
