# 主要问题与解决过程

这份记录围绕实际问题组织项目经历：先找到可复现的错误，定位原因，采用最小修复，
再用相同口径验证结果。它记录已经取得的证据，不把计划中的能力写成成果。

本轮审核起点为 `39ad06e`，时间为 2026-10-08。完整的历史审核见
[PROJECT_REVIEW.md](PROJECT_REVIEW.md)。本轮优先处理事实一致性、评测可信度、
请求统计和工具调用效率；界面润色与复杂架构暂不作为成果。

## 1. 两个工具查同一订单，却给出不同事实

**遇到的问题。** “前天收到”的订单实际被生成成一天前签收；订单表与物流轨迹
对签收时间给出了不同日期。部分待发货订单的物流描述却说已经发货。
价保案例中，购买价格也无法对应下单时生效的商品价格。
这意味着模型即使正确调用了工具，也可能拿到互相矛盾的依据。

**根因。** 订单、物流和价格种子分别维护，相对日期各自计算；原有测试只验证
“仍在退货期内”，没有验证精确天数或跨表事实。

**解决步骤。**

1. 将问题缩小到具体订单，交叉比对订单日期、物流节点和价格生效时间。
2. 统一数据生成的参考日期，让物流沿订单的发货、签收时间生成。
3. 为购买价格补充对应的生效记录，保留既定的当前售价与价保差额。
4. 用跨表回归测试验证全部适用数据，并让示例校验器检查精确签收天数。

| 检查项 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 有物流的已签收订单，签收日期一致 | 0/11 | 11/11 |
| 待发货物流描述与订单状态一致 | 0/2 | 2/2 |
| 订单明细购买价与下单时价格一致 | 9/26 | 26/26 |
| “前天收到”示例的签收天数 | 1 天 | 2 天 |

证据：[修复前](../results/data_consistency/before.json)、
[修复后](../results/data_consistency/after.json)；修复提交 `74d79fd`。
这些数字证明合成业务数据的一致性，不能直接当作模型回答正确率的提升。

**可以讲清楚的经验。** 当回答事实有误时，先核对证据来源；提示词无法解决
两个工具本身给出矛盾事实的问题。回归测试应验证业务含义，而不只是检查一个布尔标志。

## 2. 报告显示全部成功，明显错误的答案却也能通过

**遇到的问题。** 早期报告的成功率为 100%，但将答案替换为“待发货订单已发货”
或“已取消订单可以申请价保”后，仍能通过评分。35 条用例中只有 18 条有正向答案断言。

**根因。** 部分用例只检查工具与文档是否出现，没有检查回答结论。
子串匹配还会把“17 天”误认为包含正确的“7 天”，把否定句当作肯定事实。
工具精确性使用集合比较，无法识别同一工具重复调用。

**解决步骤。**

1. 先构造 12 个错误答案，并为每个反例保留一个正确答案，确认评分器确实存在漏检。
2. 给全部用例补充关键事实或结论判据，允许合理的同义表达；明确纯政策问题的禁止工具。
3. 添加数字边界和局部否定检查，按调用次数比较工具；反例被拒绝时，正确答案仍须通过。
4. 标记评分版本，保存逐条答案、错误和配置；新运行使用独立目录，禁止覆盖已有结果。

| 检查项 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 12 个已知错误答案被拒绝 | 0/12 | 12/12 |
| 有正向答案判据的用例 | 18/35 | 35/35 |

证据：[修复前](../results/eval_guardrails/before.json)、
[修复后](../results/eval_guardrails/after.json)；修复提交 `62f81b2`。
这里改善的是评分器的检错能力。评分仍是关键词与局部否定启发式，不能证明任意回答
语义正确；旧版 100% 与新版通过率不能直接比较。

在线优化又暴露了评分的另一面：保修政策已包含“充电器 18 个月、耳机 12 个月”，
正确回答却因没有再查商品说明被判失败。修正时保留政策证据要求，改为校验商品与期限
的对应关系，并验证“两个期限互换”或否定事实仍会失败；也补充了“可以一起申请退货”
这一合理表达。提交 `ae3b57b` 将评分升级为 v3，三组原始答案统一重新评分，
不只调整优化组。最终两条初判失败分别使用“一起退也是可以”和“没有可退的差价”，
事实与条件正确；提交 `69b635a` 补充对应表达及否定反例，升级至 v4。
三组原始报告仍保留，以便看清口径变化；同义表达修正不算 Agent 的能力提升。

**可以讲清楚的经验。** 优化前要先证明指标能识别错误。给评分器加入成对的正反例，
比直接追求更高的成功率更能保证后续实验有效。

## 3. 一轮回答发生三次请求，报表却只记了两次

**遇到的问题。** 检索 embedding 与对话模型各使用独立客户端，最终只汇总对话客户端。
检索的调用次数、token 和未定价状态没有进入请求报表；所谓“延迟”也只累加对话 API 耗时。

**解决步骤。** 让 Agent 与默认知识工具共享同一份 usage 账本，每轮开始清空，
每轮结束输出分阶段明细；另用计时器记录完整回答耗时。对于未配置价格的模型，
界面和评测明确显示成本估算不完整。

固定探针包含两次各 120 token 的对话请求和一次 7 token 的 embedding 请求：

| 检查项 | 修复前 | 修复后 | 实际值 |
| --- | ---: | ---: | ---: |
| 报告的 API 请求次数 | 2 | 3 | 3 |
| 报告的 token | 240 | 247 | 247 |
| 未定价 embedding 是否暴露 | 否 | 是 | 应标为部分成本 |

证据：[修复前](../results/request_accounting/before.json)、
[修复后](../results/request_accounting/after.json)；修复提交 `b74eced`。
另验证了第二轮不会继承第一轮消耗。该探针使用假的 API 响应，只验证记账完整性；
真实性能结果使用下一节的在线实验。

**可以讲清楚的经验。** 看起来成本更低，可能只是漏记了一段链路。
先统一测量范围，再讨论性能收益，且不能把未知价格当成零成本。

## 4. 工具都能调用，但同一问题反复查已有信息

**遇到的问题。** 轨迹中出现了三类重复劳动：查询订单状态后又查物流；
订单已返回现价与差价，却又查价格历史；同一个政策问题拆成多次相近检索。
原提示词把“到哪了”和“还能退吗”都引导到订单加物流，放大了调用范围。

**解决步骤。**

1. 在事实、评分和记账修复后重跑完整基线，不沿用早期弱判据的报告。
2. 明确工具各自提供的信息：订单状态、金额和签收日期只查订单；物流位置和轨迹
   使用物流工具；价保直接使用订单已返回的现价、差价和期限。
3. 检索 query 覆盖完整问题，已有依据足够时结束，缺少必要信息时才补查。
4. 第一版减少了调用，却让模型把订单窗口标志当成完整资格，跳过政策检索。
   逐条检查后，补充“判断资格仍须查政策”、二次销售条件和他人订单的直接拒绝规则。
   保留这一失败版本的结果，不能只展示最后成功的版本。
5. 使用同一模型、问题、数据库、参考日期、知识索引和定价假设进行对照，
   保存 35 条用例各 3 次的逐条结果，再检查质量与效率是否同时满足要求。

**实测结果。** 三组各 105 次，共 315 次在线尝试。下表全部按 v4 规则重新评分；
原始报告未被改写，其中前两组为 v2、最后一组为 v3。
本轮只改变提示词和工具描述，工具实现、控制流与数据结构未变。
用例全程可见，因此这是开发集上的提示词引导效果，不是架构提升或泛化能力证明。

| 指标 | 优化前 | 第一版优化 | 修正后 |
| --- | ---: | ---: | ---: |
| 规则成功率 | 98/105（93.3%） | 94/105（89.5%） | 105/105（100%） |
| 严格成功率 | 67/105（63.8%） | 91/105（86.7%） | 100/105（95.2%） |
| 工具调用总数 | 160 | 123 | 122 |
| 超出用例所需次数的调用 | 43 | 10 | 5 |
| 上述调用占工具调用比例 | 26.9% | 8.1% | 4.1% |
| 端到端耗时 p50 / p95（ms） | 2199 / 33265 | 2083 / 6263 | 2222 / 7196 |
| 平均 token / 次 | 3202 | 3179 | 3338 |
| 已定价 LLM 成本估算小计（元） | 0.315155 | 0.276748 | 0.296818 |

工具调用减少 **23.8%**，超出用例所需次数的调用减少 **88.4%**，严格成功率提高
**31.4 个百分点**。第一次优化的质量回退说明：调用少了，不代表任务完成得更好。
本轮最终版本保留政策检索，并修复了漏查政策、错误价保起算点和他人订单多查的问题。

**结果边界。**

- 严格成功要求普通成功且调用次数与用例要求完全一致。重复检索、故障补查也会被记为
  额外调用，因此该指标表达用例的调用预算，不能证明每一次补查都没有价值。
- 优化前有 6 次 embedding 内部服务错误，第一版有 3 次，最终组本次没有。
  原始耗时改善混有服务波动，不能都归因于代码。另取两组均无执行错误的 **99 个同一尝试**
  对照：调用数 145 → 114，平均耗时 3278 → 2773 ms（约下降 15.4%），
  p50 2151 → 2170 ms，平均 token 3128 → 3324。没有按是否通过评分筛选样本。
- 全量平均 token **增加约 4.2%**，中位耗时基本持平。因此这轮证明的是调用效率改善，
  尚不能宣称 token 或中位延迟改善。接口缓存、网络和服务波动仍影响耗时与成本。
- 成本按固定 peak=true 与汇率 7.2 估算，embedding 未定价，不是完整账单。
  API 计数取有 usage 的返回记录，未包含 SDK 透明重试的物理请求数。
- 100% 仅表示这批 35 条合成用例的规则通过率，不表示任意回答语义正确或生产环境可靠。
  后续应扩充独立失败案例与多轮业务，避免只围绕现有用例优化。

证据：[共同口径对照](../results/tool_efficiency/comparison.json)、
[冻结条件](../results/tool_efficiency/conditions.json)、
[优化前明细](../results/tool_efficiency/before/per_case.jsonl)、
[第一版明细](../results/tool_efficiency/initial/per_case.jsonl)、
[最终明细](../results/tool_efficiency/after/per_case.jsonl)。
流程提交为 `9c633de`、`4724792`；评分修正为 `ae3b57b`、`69b635a`。
`scripts/summarize_tool_efficiency.py` 可离线复算，使用 `--out` 指定新的结果文件。

前端“评测进展”页可逐条回放三组原始答案、调用参数、命中文档和共同 v5 评分；
v5 明确拆开指标名称，旧 v4 对照文件与原始答案继续保留，成绩不变。
例如 `pp-no-difference` 的首轮结果缺少政策检索，并错误地用签收日起算价保；
修正后的结果按下单日计算。点击“体验此用例”会切换对应模拟用户，发送后运行当前 Agent。
历史回放与实时体验分别展示，避免把保存的成绩当成当前每次运行的保证。

**可以讲清楚的经验。** 先从轨迹找到多查了什么，再修改工具信息边界。
优化出现回退时，沿失败样本检查缺了哪项证据，补回必要查询；用相同事实与评分口径
复测，同时披露没有改善的指标。这比只增加组件更能解释项目中实际解决了什么问题。

## 5. 可见用例达到 100%，换问题后还能成立吗？

**遇到的问题。** 35 条用例一直参与开发，提示词反复调整后的高分没有独立验证。
另有两个用户和多个商品覆盖不足，多轮历史虽然已支持，却没有在线会话评测。

**解决步骤。**

1. 在改变 Agent 行为前冻结独立的 15 条新增验证，用 14 个原集未使用的订单与不同问题角度；
   首次只跑一遍，保留失败和服务错误。用例作者已读过项目，不能称为严格盲测。
2. 在隔离进程中逐项删除四个提示词子句，同时做一次原提示词复跑；正式提示词不修改。
3. 冻结原 35 条定义，扩成 70 条公开开发用例：USER001 / USER002 / USER003 为
   38 / 15 / 17 条，P001–P004 均超过 3 条，待发货与取消订单各覆盖 5 条，
   54/70 条指定禁止工具，含 10 条多轮会话和 4 条库外问题。
4. 同一会话保留历史，每轮单独判定，任何一轮失败都不能被最后一轮的正确答案遮盖；
   汇总全会话请求消耗与错误。重要政策另检查支撑答案的小节，保存每次检索排名。

| 新增验证实验（各 15 条、1 遍） | 规则通过 | 严格通过 | 含执行错误的尝试 |
| --- | ---: | ---: | ---: |
| 冻结后的首次运行 | 11/15 | 10/15 | 1 |
| 不改提示词的复跑对照 | 12/15 | 11/15 | 0 |
| 删除“订单只查订单”子句 | 13/15 | 12/15 | 0 |
| 删除“物流调用范围”子句 | 11/15 | 11/15 | 0 |
| 删除“退货价保必须查政策”子句 | 13/15 | 12/15 | 0 |
| 删除“完整问题检索”子句 | 13/15 | 12/15 | 0 |

首次失败包括状态问题多查物流、价保漏查政策，以及一次 embedding 异常；
异常用例最终答对，但仍判失败，不剔除。价保答案还触发了狭窄的同义表达规则。
单次 15 条样本、服务波动和调用预算不能支持“低于 80% 就证明主要过拟合”的结论，
也不能据“删除后分数不降”认定某条安全规则只是记忆题目。正式规则本轮全部保留。
能够确认的是：旧 100% 没有代表新问题的表现，后续需要独立来源与重复验证。
这些问题现在已经公开，后续不再称为未见留出集。

证据：[首次原始记录](../results/holdout/first/per_case.jsonl)、
[不改提示词的复跑](../results/holdout/control_repeat/summary.json)、
[四项消融](../results/holdout/ablation/)、
[70 条开发用例](../data/eval/development.yaml)。
指标拆分与多轮实现为 `d24c653`、`b254db7`，扩集为 `f6cd51e`。
新增用例没有要求修改主提示词；检索改进使用公开开发查询，不能再充当独立验证。

## 6. 旧索引会返回过期政策，库外问题也总能“命中”

**遇到的问题。** 源文档从“7 天”改成“30 天”后，原索引仍可加载并返回旧政策。
另外，只要问题非空，FAISS 就会给出前三名；相似不等于有答案，`found=true` 因此失真。

**解决步骤。**

1. 用临时文档复现过期政策，再对源文件内容、切分配置与版本记录指纹；加载和内存检索
   均校验，构建期间文档变化也拒绝写入。纯标题小节不入索引，保留其他 chunk ID。
2. 先冻结 30 条真实检索采样问题，观察模型分数后标定；标定绑定模型、知识内容和切分版本。
3. 首版单阈值使开发集库外拒答达到 4/4，但误拒 P002 的 LDAC、佩戴调节与 P004 的
   金属物品问题。总分上涨掩盖了正向检索回退，保留这个版本，继续检查有效问题。
4. 在商品段落的 embedding 标题保留型号编号，补入公开开发集实际检索 query 与 SKU 库外反例。
   正反样本分数仍重叠，因此较弱分数直接拒绝，重叠区间按候选正文核验证据，强分数保留。
   核验只发生在该区间，用同一请求账本记录 `kb_relevance`，不作为评测的主评分器。

| 可复现检查 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 修改源文档后仍返回旧政策 | 是 | 明确拒绝并要求重建 |
| 纯标题小节 | 3 | 0 |
| 索引小节数 / 文档数 | 51 / 8 | 48 / 8 |

证据：[过期索引复现前](../results/rag_integrity/before.json)、
[修复后](../results/rag_integrity/after.json)。这两个探针为离线验证，不能证明真实语义排序。
指纹修复为 `afcb6ad`；修正误拒并保存证据为 `db238d6`。

真实 API 的固定采样复测共 81 个问题（原 30 条与新增 51 条）：
58 条库内有依据的问题保留 57 条，23 条库外全部拒绝；独立于边界选择的 validation
子集为 10 条有效、6 条库外，均符合预期。首版新增的三条误拒已恢复。
剩下一条 P002 快充问题的正确段落没有进入前三名，在未过滤的基线中也已漏命中；
拒绝错误候选不能代替找回正确证据。样本规模小，强分数也未必相关，不能当作通用阈值。

采样复测触发 3 次批量 embedding 和 6 次证据核验，共 9 次请求、3539 token；
核验 LLM 已定价小计 0.002778 元，embedding 未定价，不能称为完整成本。
离线探针也验证 2 次 Agent 请求 + 1 次检索 + 1 次核验全部计入，367 token 无遗漏。
证据：[原分布](../results/relevance/calibration.json)、
[型号编号与重叠分布](../results/relevance/with_identifiers.json)、

## 8. RRF 融合后遗漏退货条件：先补位，再测重排

**遇到的问题与根因。** 一般退货期限需要同时覆盖七天无理由和十五天质量问题。
RRF 将保修、政策简介、七天条款排在前三名，将包含两种期限的对照表排第四。
融合依据名次投票，不能判断一个章节是否覆盖全部条件；先截前三名再核验，
过滤了无关章节后不会自动补入第四名。这不是知识库缺少数据。

**解决步骤。**

1. 原 52 条已公开问题全部用于开发；增加并先冻结 20 条新验证，正文不变。
   多事实问题分别要求充分章节，不用“命中同一文档”代替事实覆盖。
2. 加入核验后补位：核验最多 10 个候选，再返回最多 3 个有效片段。
   确认第四名能补入，并用库外问题检查核验池扩大后有没有误接受。
3. 接入 `BAAI/bge-reranker-v2-m3` API，按问题与章节正文重排同一 RRF 候选池。
   保存各路分数与排名，重排高分仍须正文核验；用离线反例验证高分无关内容不能通过。
4. 分开测 BM25、RRF、补位、重排、重排＋补位。最终片段数上限都是 3，
   另外记录核验池、token 和每段请求耗时，不将扩大核验预算说成零成本算法提升。
5. 根据开发结果冻结部署选择后再跑新验证；前端用保存的原始记录提供回放。
   同一请求的对话、embedding、重排与核验共享账本；API 错误可见，不静默切换方案。

**结论与代价。** 两种改进都找回遗漏的质量条件；补位改变的是过滤顺序，
重排改善的是前三名排序。重排分数不是回答正确率，不能替代事实核验。

同一事实的多个相似章节会挤掉第二项事实；单个配对相关性分数不能保证多事实覆盖。

## 9. 刷新后丢失对话，同一用户无法继续原会话

本节保留阶段 1 的历史实现与测试。阶段 2 按用户要求取消客户登录，继续保留会话存储；
匿名 401 等认证结论不适用于当前模拟用户模式，见下节。

**遇到的问题。** 订单和政策对话可以连续追问，但刷新页面或重启服务后，
Agent 的消息与 Gradio 会话状态消失，用户需要重新提供订单。界面下拉可选择业务用户，
只适合模拟身份，不能作为持久历史和未来售后写操作的认证入口。

**根因。** 消息和 Agent 对象只存在于进程内，业务数据库未保存对话。
业务工具虽然校验订单所属用户，但应用的用户身份此前由界面选择。
把聊天框内容直接传回模型也不能解决恢复：显示数据可以被客户端伪造。

**解决步骤。**

1. 在实现前冻结 10 项结构性验收，区分对话恢复、身份隔离、并发和中断。
   使用 Gradio 内置登录，服务器将已验证登录名映射到业务用户；独立演示密码保存在
   被忽略的 `.env`，没有把它们写入源码或评测记录。
2. 追加带版本的 SQLite 迁移，保存会话所属用户和逐轮消息。
   原始模型消息保留完整的工具请求与返回，重新建立 Agent 时恢复它们。
   当前系统提示来自代码，历史消息不能替换当前提示；浏览器历史不是可信模型上下文。
3. 请求开始先落库，完成后将模型消息、回复与可观测统计原子保存。
   同会话第二个请求在模型调用前被拒绝，不持有数据库事务等待外部 API。
   中断请求保留标记与用户输入，残缺工具调用不用于下一轮。
4. 刷新、重登和重启后先列出本人历史，由用户显式选择继续；新会话没有旧上下文。
   加载与写入按会话和用户共同校验，订单仍由业务数据层校验所有者。
5. 重启标记未完成请求，不自动重放；恢复后提示重新查询当前业务条件。
   旧种子脚本在已有会话时拒绝重建，避免升级时破坏历史或业务事实。

**验证与量化边界。** 离线回归检查进程间恢复、工具配对、跨用户拒绝、并发只保留
一个请求、重复迁移与重建保护。真实浏览器确认匿名接口返回 401；首轮订单对话
有 197 次正文增量变化，退出再登录并恢复后追问原订单号，有 11 次增量变化且回答正确。
实际重启后已完成轮次与工具结果仍存在，故障注入的未完成请求标为中断，未自动重放。
另一账户看不到该会话，订单选择仅包含该账户订单；输入框仍可用。

以上是代表性功能检查和结构性保证，不是线上模型记忆准确率。任务字段正确性、
重复追问次数、退货副作用与管理员审核尚未评测，也未宣称完成。
当前采用单进程服务，不能将其启动恢复逻辑直接用于多个实例共享数据库。

证据：[冻结验收](../results/session_memory/frozen_manifest.json)、
[真实浏览器记录](../results/session_memory/browser_check.json)。
测试脚本的等待、标签大小写与虚拟表格选择失败另存，不删掉记录或当作模型失败；
通过调整验证定位方式完成检查，没有因此放宽账户与恢复条件。

**可以讲清楚的经验。** 历史存储、模型上下文与当前业务事实分开管理。
恢复对话不等于恢复业务授权，旧工具结果也不等于当前状态；后续提交须重新校验。

## 10. 对话记住订单，办理草稿仍会因暂停或更正丢失

**问题。** 持久对话可以回放消息，但没有明确的当前申请信息。“之前买的耳机”无法
通过 Agent 查询订单候选；换订单时，旧商品、数量与原因没有统一的失效规则。
本阶段真实模型首测还发现：用户说“你好，先不用继续退货”，模型把暂停理解为中止，
调用工具清空了刚记录的订单、明细、数量、原因和未拆封信息。下一轮要求回顾时，
它反而要求重新开始提供订单与商品。

**根因。** 历史文字、当前任务状态和业务事实是不同的数据。只有消息历史不能保证
草稿的字段来源、跨重启恢复和依赖清理。即使提示词要求暂停不清空，模型对模糊意图的
解释也可能出错；允许模型无条件清空草稿会把这个解释错误变成持久状态错误。

**解决步骤。**

1. 先冻结 12 项结构场景和 6 段在线对话。基线 `66378c2` 没有订单候选工具或任务表；
   新增回归先因缺少对应工具、存储方法和表而失败。这是能力缺口，不是模型成功率 0%。
2. 按用户要求移除客户登录，恢复合成用户选择，保留原会话。后台继续按所选用户校验
   订单、会话和明细归属；模拟身份不等于认证，当前只演示合成数据。
3. 提供 `list_orders`，候选带实际商品明细。多候选或多商品需澄清，不能擅自选择。
   SQLite v2 迁移追加每会话一份草稿；三个任务工具绑定服务端会话与当前轮次，模型
   无法通过参数选择其他会话。
4. 保存结构字段、原始用户轮次与修订版本。订单或明细更正后清理相应旧依赖；
   非整数、非正数、超过购买量、跨订单明细等输入在事务内拒绝，原草稿保持不变。
   用户自述与实时订单数据分别返回；未拆封和质量问题不视为审核事实，质量凭证仍待补充。
5. 首测保留失败后，给中止工具加后台表达约束：明确的“中止/取消/清空退货草稿”才可
   清理，暂停话题和否定中止被拒绝；补正反例，模型误调用也不能清空。此规则只覆盖
   支持的明确表达，不宣称解决所有自然语言歧义；不能识别时请用户明确重述。
6. 每轮恢复时提供当前结构字段，原话来源完整留库，避免在新增系统上下文重复展开
   每个字段的同一原话。左侧显示草稿与待补字段，刷新和实际重启后显式恢复；新会话
   和用户切换清空当前界面上下文，原历史保留。只要求记录时不主动判断退货资格。

## 11. 从退货草稿到申请：工具调用正确，仍可能解释错政策或重复写单

**问题。** 阶段 2 可以记住订单和退货字段，但不能创建申请。加入写操作后，聊天里
一句“确认”不能直接成为授权；旧草稿、已用数量和失败重试也不能直接用来写单。
真实模型首测中，5 段申请状态检查全部通过，回答却在 3 段擅自添加“赠品/发票”条件，
另 2 段把签收 13 天的质量问题放进 7 天窗口，遗漏实际适用的 15 天质量政策。

**根因。** 草稿完整不代表当前资格成立；工具返回成功也不能证明最终解释正确。
订单工具的 `within_return_window` 仅表示无理由 7 天窗口，模型容易把它当成通用资格。
草稿工具最初只返回待补字段，没有同时提供对应的政策条件，模型用常识补齐了店铺
没有规定的条款。随后返回完整政策虽消除了额外条款，却让模型把无理由的二次销售
条件套到质量问题上。申请创建还需要独立处理当前事实、授权、数量竞争与响应丢失。

**解决步骤。**

1. 在实现前冻结 18 项结构性场景和 5 段、6 轮模型对话。基线 `d138e65` 缺少申请
   模块，新增测试先无法收集；这是未具备能力，不记作模型成功率 0%。评测复制原
   业务事实到临时数据库，固定日期 2026-10-13；不重置演示库来制造可退订单。
2. 从现有政策文件读取期限、运费和条件，核对正文与规则表一致，保存版本及 hash。
   无理由使用 7 天、二次销售声明；质量使用 15 天、非人为功能故障声明及照片/视频。
   用户陈述与上传保留来源，但不当成已审核事实。政策正文和检索索引保持不变。
3. 预览只保存待确认内容。正式提交只由页面按钮触发，模型没有提交或退款工具；
   后台重新检查用户、订单、明细、签收日期、原因、凭证及剩余数量。草稿修订、撤回
   声明、撤下凭证、政策变化或过期均使原预览失效。补充商品事实变化的反例后，
   修复确认时未比较商品身份的缺口；已提交任务锁定，不能把中止草稿当撤回申请。
4. 在同一个 SQLite 写事务中消费确认、创建待审核单、写审计并关联任务。相同预览
   重试返回同一单据；数据库数量约束阻止不同会话超量，事务异常不残留半张申请。
   回复丢失时提示查询实际结果，不能把响应失败说成业务未提交；刷新或重启可恢复。
5. 首测错误保留后，让草稿工具提供同源政策，再改为只提供当前原因的政策分支。
   不放宽评测判据，分别核对状态与回答。左侧订单改为全量滚动，页面增加预览、
   确认、上传和状态查询，浏览器检查真正的交互链路。

**验证结果。** 完整离线回归 310 项及 Ruff 通过，包含跨用户、7/8 与 15/16 天边界、
   并发余量、过期/更正、凭证撤回、迁移、事务故障及提交后响应丢失。相同 5 段模型
   状态检查仍为 5/5；最终逐条阅读答案与轨迹，未再发现上述额外条件或跨原因政策
   错误。取消订单回复仍带一条英文开场白，完整表达规范尚未全部满足。不能将这些
   已看过的合成场景称为未见测试成绩，也不据此宣称总体客服成功率提升。

初次真实浏览器 8 项检查通过，确认前 0 张申请，按钮确认后 1 张待审核单；刷新查询
不增加记录。USER001 的 10 笔订单全部渲染，190px 区域可滚动到最后一笔；用户切换
过滤订单与申请。首轮正文有 247 次增量变化。最终恢复及凭证撤回检查另存，之前的
浏览器结果与最终代码版本分别标识；最终 4 项检查通过，无页面脚本错误，包括恢复
已提交任务、撤下凭证失效、重新上传预览和带附件切换用户，未新增申请。
演示库保留这张合成申请，没有清库或实际退款。

**边界与经验。** 模型负责理解、整理及解释，申请是否能写入由后台当前事实与事务
决定。状态正确、政策解释正确、交互可用分别测量，才能看到“工具全对、回答仍错”
的问题。照片仅检查格式，MP4 仅检查文件头；质量真实性仍待审核。管理员审核、
仓库验收、真实退款、长对话预算与多实例恢复尚未实现；不从单次调用宣称延迟或成本

## 12. 检索没有命中，不等于店内没有商品；完整知识也不保证回答正确

**问题。** 用户要求挂耳、不完全入耳、跑步使用、500 元以内，实际对话没有正确利用
两款耳机的完整目录。另有回答承诺转人工或让用户点击不存在的人工入口。以相同
场景复现时，基线还把签收第 15 天的质量退货判成过期；小知识库是否需要复杂检索
也缺少与全文、整篇文档的直接对照。

**根因。** 数据层已有商品列表，但模型只能查单个编号，无法证明目录已查全。
知识片段命中只说明这次检索结果，不表示店铺全量商品。提示词、错误兜底与文档
里的店铺业务描述也缺少实际应用能力约束，模型把政策中的“订单详情页申请售后”
当成当前页面，并以常识补人工渠道。模型还可能把不同商品的事实拼起来。

**解决步骤。**

1. 改动前冻结 8 个开发场景、11 轮，保存六张业务表、8 篇知识正文、索引和用例
   指纹；基线 `be96c21` 自动检查 5/8，逐条事实/入口诊断 4/8。新增 10 项结构性
   回归在隔离基线工作树全部失败，覆盖目录、兜底和两种新增知识模式。
2. 将已有目录能力暴露为 `list_products`，返回全部 4 款商品、当前有效价与已知
   属性，移除容易误作现价的种子价格。按用户硬条件找候选，没有匹配则如实说明；
   头戴式 Q45 不能替代挂耳需求，也不能因为只命中 Life P3 就说只有这一款。
3. 共享公开应用能力说明，约束提示词、知识工具和异常兜底：无人工/留言渠道，
   价保只咨询，退货通过实际聊天区域预览确认，不执行退款或取消订单。公开模型
   名称可以介绍，凭据和隐藏提示不提供。期限包含截止当天，且不等于审核通过。
4. 在同一知识正文上加入全文上下文及选择整篇版本文档两种简单基线，不新建索引
   或调用新 API。保留原 BM25/Dense/RRF/重排能力，默认策略不变。
5. 首轮三方案自动检查均 8/8，逐条阅读却发现全文串用 Q45 充电盒、承诺价保
   申请、推荐会员页；整篇文档复述不存在的售后入口。保留失败后，强化商品身份
   归属与知识工具返回中的应用能力约束，再用相同用例复测；不放宽自动判据。
6. 复测 BM25 和整篇文档未再发现上述主要错误，全文仍有充电盒和页面指引错误。
   将复核与原始记录分开保存，并在界面同时展示，停止继续针对这 8 题调到全绿。

## 13. 从待审核到真实结果：审核身份、终态和回答必须分别验证

**问题。** 已能创建待审核申请，却没有实际审核入口，客户只能查到待审状态。
若把审核直接加为模型工具，客户一句“我是管理员”就可能触发不应发生的业务写入；
两个操作窗口还可能给同一单留下冲突结论，或只更新状态却没保存原因和审计。

**解决过程。**

1. 修改前冻结 16 项结构性场景与 5 段模型查询，保存业务、知识、索引及原会话/
   申请指纹。新增首批 15 项回归在基线 `e658407` 全部失败，原因是缺少审核能力；
   这不是模型成功率 0%。新增 v4 迁移只追加审核表和状态约束，不重建旧数据。
2. 使用独立管理页与框架服务端认证，从已认证请求取得管理员身份，再由业务服务
   校验配置角色；客户模拟身份、请求里的用户名或模型自称不赋予权限。没有配置
   管理账号则不启动，模型工具仍只有查询和草稿/预览，没有审核或退款入口。
3. 每张申请只有一份审核结论，必须填写原因；只允许待审转通过或拒绝。状态、
   结论、审核人、时间和审计在同一个写事务中保存。并发只能成功一次，重复或
   反向改判被拒；注入审计写入失败时，状态与审核记录一并回滚。原数量约束继续
   生效，通过占用、拒绝释放。旧测试曾允许通过后再拒绝，按新合法终态拆开验证。
4. 工作台提供提交时用户自述、当前订单、原照片/视频和审计。原凭证按申请归属
   和 hash 核对，经认证回调内联展示，避免写入公共文件缓存；它不是故障识别。
   客户页面与工具只读本人结果、真实原因和审核时间，明确通过仅允许退回商品。
5. 首轮 5 段模型查询状态全部正确，阅读却发现通过回复承诺查退件物流、漏审核
   原因，跨用户拒绝又指向不存在的客户登录。保留原记录后补真实能力说明，复测
   这 5 段：前述主要错误未再发现。仍有泛指联系店铺的建议，作为表达限制记录。
6. 真实浏览器在业务副本走完登录、拒绝伪造身份、查看凭证、空原因拒绝、通过、
   拒绝与客户查询；不审核演示库原申请。最终只读复核复用两次已有决定，不再
   创建申请或审核。客户默认收起工程观察，勾选后仍能实时查看轨迹。

| 验证维度 | 实测结果 | 能说明什么 |
| --- | --- | --- |
| 离线约束与回归 | 345 项及 Ruff 通过 | 角色、非法/重复/并发审核、事务回滚、数量、迁移与历史功能 |
| 同一 5 段模型状态检查 | 首测、复测均 5/5 | 模型查询不改变申请或审核；不等于回答正确 |
| 主要事实/入口阅读诊断 | 3/5 → 5/5 | 本批退件查询/登录入口承诺与审核原因遗漏修正 |
| 浏览器 | 8 项流程、最终展示 3 项通过 | 真实认证和查询链路；管理页 1280/375/320px 无横向溢出 |
| 原数据 | 业务、会话、申请、知识和索引指纹保留 | 不靠清库、改日期或改政策制造可演示结果 |

阅读诊断由 Codex 完成，未经外部人工独立审核。场景已见、各跑一遍，不是总体或

## 14. 历史能保存，不代表每次模型输入和整轮执行有边界

**问题与根因。** 原先 `app.py` 同时管理轮次、恢复、模型消息和保存；草稿评测直接
依赖 UI。每次把全部已存消息重新交给模型，只有 step 上限，没有整轮时间、请求数和
输入上限。用合成长历史可以复现输入持续增长；这不是已经发生过的生产超限事故。
单次 HTTP read timeout 会被持续到来的片段重置，也不能证明一个流会在整轮预算内结束。

**解决过程。**

1. 提取 `ChatService.run_turn`，界面只渲染流式更新，草稿评测直接调用同一服务。
   SQLite 先预留轮次再释放事务，最多两个活动会话，第三个显示排队；同会话拒绝并发。
2. 根据完整用户轮次裁剪近期上下文，保留工具请求/返回配对、当前规则、用户问题和
   结构化任务；原始消息不删除。每次模型输入重新检查必要内容，超限明确停止。
3. 将120秒/16次API/12个工具/4次知识查询与原6个step一起作为运行边界；核验、
   embedding、reranker共用账本。外部请求使用可取消I/O和整段响应截止时间，关闭
   SDK 隐式重试，失败但缺失usage的请求也记录为不完整消耗。
4. 超限工具批次为未执行调用补结构化停止返回，使消息配对完整；断流保留部分回答，
   取消生成器释放连接和会话预留。中断恢复与正式提交/审核仍使用原事务链路。

**量化证据。** 固定 v2 数据、19轮合成历史、同一退货草稿和同一数量更正问题，分别
用100,000字符的宽松上限与24,000字符上限运行各一次。宽松组近似旧的全历史策略，
不是旧提交的完整质量对照。

| 指标 | 宽松组 | 有界组 |
| --- | --- | --- |
| 首次输入字符（含消息/schema的JSON） | 46,225 | 23,463 |
| 保留历史轮数 | 19 | 7 |
| 整轮输入token（提供商usage，含两次请求） | 50,848 | 24,160 |
| API请求数 | 2 | 2 |
| 订单/明细/原因不变、数量改为1 | 通过 | 通过 |
| SQLite保存的用户/客服消息 | 40 | 40 |

该探针整轮输入token下降约52.5%，两个方案都正确保存任务。没有证明其他长对话都
能维持正确率，也没有据单次耗时声称 P50/P95 提升。裁剪不是摘要或长期记忆。
原始回答、工具返回、任务状态、运行条件与hash见
[长历史探针](../results/runtime_service/context_probe_final/summary.json)。

**场景数据与工作台。** 新场景独立生成12个合成型号、24个SKU、60订单和75明细，
覆盖7/8、15/16天边界、多明细、数量大于1、已占用售后数量、缺货和未知状态；原库
六张业务表与既有申请保留。颜色/SKU进入订单、申请预览与审核快照，旧数据仍未知。
数据增加属于覆盖扩展，不作为 Agent 回答质量提升。

8个开发冒烟场景的执行检查通过，记录完整目录、硬条件无匹配、颜色库存、越权及
期限边界。首次回答仍出现“让朋友登录”这一不存在的入口指引；保留首测，明确
身份能力说明后再次运行。逐条阅读诊断、自动执行检查分别保存，后者不能代替答案
正确性判定。当前未交付80段多轮留出或外部基准。

界面参考开源项目实际源码，采用历史/聊天/业务分栏与固定输入区；浏览器检查覆盖

## 15. 多轮任务实际运行后，预算、部署与评分器各自暴露问题

**问题。** 之前的8条冒烟只能证明能执行，不能代表多轮业务成功。新增80段任务后，
用户第一句明确提供订单号仍会触发`context_limit`，后面反复追问已经说过的订单。
容器页面健康不代表直接调用同一个服务也能找到知识；自动评分也会把正确回复判错。

**定位。** 首个开发反例的`list_orders`返回20笔完整单据，包含重复的价格计算、
完整SKU属性和非定位字段。与政策及工具schema合并后达24,082字符，超过24,000
上限；第一轮未保存任务，后续丢失上下文是该次拒绝的连锁表现，不是数据库丢数据。
另外，多商品订单虽然已经明确选定订单，Agent有时只追问商品而不保存已知订单，
这是独立的任务记忆失败，不能都归因于输入长度。

容器的UI和健康脚本主动把`src`加入路径，而直接导入安装包时`PROJECT_ROOT`指向
site-packages，知识目录不存在。原构建还把源码和依赖安装放在同层，改文档会重下
全部依赖；实际一次重建因PyPI TLS中断失败。

评分器最早在20个成对样例中误接受了一条错误政策回答。补原文引用后，完整任务又
暴露输入证据缺失：只有目标明细却被当成整个订单；缺物流事实；分开给所有回复与
最终可信操作，导致把后来的上传、确认回溯到之前的回答。即使补事件顺序，短句
校准也不能证明长对话裁判可靠；完整开发对话中仍有矛盾结论和输出不完整。

**处理。**

1. 订单候选只返回定位所需的订单/明细/数量/所购颜色；完整金额、差价、日期与SKU
   详情继续由`get_order`查询。先用相同工具批次的回归复现失败，再通过修复。
2. 容器明确统一源码路径；基础镜像从官方GHCR取得并固定digest，依赖层与源码分开，
   使用uv缓存。真实跑查询、上传、明确确认、审核、故障、索引和迁移，再停止及删除
   重建容器验证数据卷，而不是仅检查页面HTTP 200。
3. 冻结40开发/40留出、8类共80段及业务快照，实际执行开发1次、留出3次，保留160次
   运行的全部回复和SQL检查。用户脚本由Codex编写，不伪装为真实客户语料或严格盲测。
4. 所有初次评分保留；给裁判完整订单、物流、政策和有序的工具/操作/任务状态。
   用完整开发对话与成对变异校准，再重评相同原始回答，不重跑Agent挑选好答案。
   无效结构、缺少可追溯引用或推理输出耗尽均记为`judge_error`，不静默通过。
5. 固定原版τ retail版本、任务0–4、三个种子和同模型官方对照；接入实际ACS Loop，
   原环境执行工具、原断言评分，不把本地业务规则替换进去。

**可复核结果。** 候选返回11,848→5,351字符，减少约54.8%，20笔订单和25条明细
全部保留，输入上限仍为24,000。该数字是工具返回字符量，不是token、速度或成功率
提升。相同强制调用反例从`context_limit`变为正常回答，证据见
