# 主要问题与解决过程

这份记录围绕实际问题组织项目经历：先找到可复现的错误，定位原因，采用最小修复，
再用相同口径验证结果。它记录已经取得的证据，不把计划中的能力写成成果。

本轮审核起点为 `39ad06e`，时间为 2026-10-08。完整的历史审核见
[PROJECT_REVIEW.md](PROJECT_REVIEW.md)。本轮优先处理事实一致性、评测可信度、
请求统计和工具调用效率；界面润色与复杂架构暂不作为成果。

## 1. 两个工具查同一订单，却给出不同事实

**遇到的问题。** “前天收到”的订单实际被生成成一天前签收；订单表与物流轨迹
对签收时间给出了不同日期。部分待发货订单的物流描述却说已经发货。
价保案例中，购买价格也无法对应下单时生效的商品价格。
这意味着模型即使正确调用了工具，也可能拿到互相矛盾的依据。

**根因。** 订单、物流和价格种子分别维护，相对日期各自计算；原有测试只验证
“仍在退货期内”，没有验证精确天数或跨表事实。

**解决步骤。**

1. 将问题缩小到具体订单，交叉比对订单日期、物流节点和价格生效时间。
2. 统一数据生成的参考日期，让物流沿订单的发货、签收时间生成。
3. 为购买价格补充对应的生效记录，保留既定的当前售价与价保差额。
4. 用跨表回归测试验证全部适用数据，并让示例校验器检查精确签收天数。

| 检查项 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 有物流的已签收订单，签收日期一致 | 0/11 | 11/11 |
| 待发货物流描述与订单状态一致 | 0/2 | 2/2 |
| 订单明细购买价与下单时价格一致 | 9/26 | 26/26 |
| “前天收到”示例的签收天数 | 1 天 | 2 天 |

证据：[修复前](../results/data_consistency/before.json)、
[修复后](../results/data_consistency/after.json)；修复提交 `74d79fd`。
这些数字证明合成业务数据的一致性，不能直接当作模型回答正确率的提升。

**可以讲清楚的经验。** 当回答事实有误时，先核对证据来源；提示词无法解决
两个工具本身给出矛盾事实的问题。回归测试应验证业务含义，而不只是检查一个布尔标志。

## 2. 报告显示全部成功，明显错误的答案却也能通过

**遇到的问题。** 早期报告的成功率为 100%，但将答案替换为“待发货订单已发货”
或“已取消订单可以申请价保”后，仍能通过评分。35 条用例中只有 18 条有正向答案断言。

**根因。** 部分用例只检查工具与文档是否出现，没有检查回答结论。
子串匹配还会把“17 天”误认为包含正确的“7 天”，把否定句当作肯定事实。
工具精确性使用集合比较，无法识别同一工具重复调用。

**解决步骤。**

1. 先构造 12 个错误答案，并为每个反例保留一个正确答案，确认评分器确实存在漏检。
2. 给全部用例补充关键事实或结论判据，允许合理的同义表达；明确纯政策问题的禁止工具。
3. 添加数字边界和局部否定检查，按调用次数比较工具；反例被拒绝时，正确答案仍须通过。
4. 标记评分版本，保存逐条答案、错误和配置；新运行使用独立目录，禁止覆盖已有结果。

| 检查项 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 12 个已知错误答案被拒绝 | 0/12 | 12/12 |
| 有正向答案判据的用例 | 18/35 | 35/35 |

证据：[修复前](../results/eval_guardrails/before.json)、
[修复后](../results/eval_guardrails/after.json)；修复提交 `62f81b2`。
这里改善的是评分器的检错能力。评分仍是关键词与局部否定启发式，不能证明任意回答
语义正确；旧版 100% 与新版通过率不能直接比较。

在线优化又暴露了评分的另一面：保修政策已包含“充电器 18 个月、耳机 12 个月”，
正确回答却因没有再查商品说明被判失败。修正时保留政策证据要求，改为校验商品与期限
的对应关系，并验证“两个期限互换”或否定事实仍会失败；也补充了“可以一起申请退货”
这一合理表达。提交 `ae3b57b` 将评分升级为 v3，三组原始答案统一重新评分，
不只调整优化组。最终两条初判失败分别使用“一起退也是可以”和“没有可退的差价”，
事实与条件正确；提交 `69b635a` 补充对应表达及否定反例，升级至 v4。
三组原始报告仍保留，以便看清口径变化；同义表达修正不算 Agent 的能力提升。

**可以讲清楚的经验。** 优化前要先证明指标能识别错误。给评分器加入成对的正反例，
比直接追求更高的成功率更能保证后续实验有效。

## 3. 一轮回答发生三次请求，报表却只记了两次

**遇到的问题。** 检索 embedding 与对话模型各使用独立客户端，最终只汇总对话客户端。
检索的调用次数、token 和未定价状态没有进入请求报表；所谓“延迟”也只累加对话 API 耗时。

**解决步骤。** 让 Agent 与默认知识工具共享同一份 usage 账本，每轮开始清空，
每轮结束输出分阶段明细；另用计时器记录完整回答耗时。对于未配置价格的模型，
界面和评测明确显示成本估算不完整。

固定探针包含两次各 120 token 的对话请求和一次 7 token 的 embedding 请求：

| 检查项 | 修复前 | 修复后 | 实际值 |
| --- | ---: | ---: | ---: |
| 报告的 API 请求次数 | 2 | 3 | 3 |
| 报告的 token | 240 | 247 | 247 |
| 未定价 embedding 是否暴露 | 否 | 是 | 应标为部分成本 |

证据：[修复前](../results/request_accounting/before.json)、
[修复后](../results/request_accounting/after.json)；修复提交 `b74eced`。
另验证了第二轮不会继承第一轮消耗。该探针使用假的 API 响应，只验证记账完整性；
真实性能结果使用下一节的在线实验。

**可以讲清楚的经验。** 看起来成本更低，可能只是漏记了一段链路。
先统一测量范围，再讨论性能收益，且不能把未知价格当成零成本。

## 4. 工具都能调用，但同一问题反复查已有信息

**遇到的问题。** 轨迹中出现了三类重复劳动：查询订单状态后又查物流；
订单已返回现价与差价，却又查价格历史；同一个政策问题拆成多次相近检索。
原提示词把“到哪了”和“还能退吗”都引导到订单加物流，放大了调用范围。

**解决步骤。**

1. 在事实、评分和记账修复后重跑完整基线，不沿用早期弱判据的报告。
2. 明确工具各自提供的信息：订单状态、金额和签收日期只查订单；物流位置和轨迹
   使用物流工具；价保直接使用订单已返回的现价、差价和期限。
3. 检索 query 覆盖完整问题，已有依据足够时结束，缺少必要信息时才补查。
4. 第一版减少了调用，却让模型把订单窗口标志当成完整资格，跳过政策检索。
   逐条检查后，补充“判断资格仍须查政策”、二次销售条件和他人订单的直接拒绝规则。
   保留这一失败版本的结果，不能只展示最后成功的版本。
5. 使用同一模型、问题、数据库、参考日期、知识索引和定价假设进行对照，
   保存 35 条用例各 3 次的逐条结果，再检查质量与效率是否同时满足要求。

**实测结果。** 三组各 105 次，共 315 次在线尝试。下表全部按 v4 规则重新评分；
原始报告未被改写，其中前两组为 v2、最后一组为 v3。
本轮只改变提示词和工具描述，工具实现、控制流与数据结构未变。
用例全程可见，因此这是开发集上的提示词引导效果，不是架构提升或泛化能力证明。

| 指标 | 优化前 | 第一版优化 | 修正后 |
| --- | ---: | ---: | ---: |
| 规则成功率 | 98/105（93.3%） | 94/105（89.5%） | 105/105（100%） |
| 严格成功率 | 67/105（63.8%） | 91/105（86.7%） | 100/105（95.2%） |
| 工具调用总数 | 160 | 123 | 122 |
| 超出用例所需次数的调用 | 43 | 10 | 5 |
| 上述调用占工具调用比例 | 26.9% | 8.1% | 4.1% |
| 端到端耗时 p50 / p95（ms） | 2199 / 33265 | 2083 / 6263 | 2222 / 7196 |
| 平均 token / 次 | 3202 | 3179 | 3338 |
| 已定价 LLM 成本估算小计（元） | 0.315155 | 0.276748 | 0.296818 |

工具调用减少 **23.8%**，超出用例所需次数的调用减少 **88.4%**，严格成功率提高
**31.4 个百分点**。第一次优化的质量回退说明：调用少了，不代表任务完成得更好。
本轮最终版本保留政策检索，并修复了漏查政策、错误价保起算点和他人订单多查的问题。

**结果边界。**

- 严格成功要求普通成功且调用次数与用例要求完全一致。重复检索、故障补查也会被记为
  额外调用，因此该指标表达用例的调用预算，不能证明每一次补查都没有价值。
- 优化前有 6 次 embedding 内部服务错误，第一版有 3 次，最终组本次没有。
  原始耗时改善混有服务波动，不能都归因于代码。另取两组均无执行错误的 **99 个同一尝试**
  对照：调用数 145 → 114，平均耗时 3278 → 2773 ms（约下降 15.4%），
  p50 2151 → 2170 ms，平均 token 3128 → 3324。没有按是否通过评分筛选样本。
- 全量平均 token **增加约 4.2%**，中位耗时基本持平。因此这轮证明的是调用效率改善，
  尚不能宣称 token 或中位延迟改善。接口缓存、网络和服务波动仍影响耗时与成本。
- 成本按固定 peak=true 与汇率 7.2 估算，embedding 未定价，不是完整账单。
  API 计数取有 usage 的返回记录，未包含 SDK 透明重试的物理请求数。
- 100% 仅表示这批 35 条合成用例的规则通过率，不表示任意回答语义正确或生产环境可靠。
  后续应扩充独立失败案例与多轮业务，避免只围绕现有用例优化。

证据：[共同口径对照](../results/tool_efficiency/comparison.json)、
[冻结条件](../results/tool_efficiency/conditions.json)、
[优化前明细](../results/tool_efficiency/before/per_case.jsonl)、
[第一版明细](../results/tool_efficiency/initial/per_case.jsonl)、
[最终明细](../results/tool_efficiency/after/per_case.jsonl)。
流程提交为 `9c633de`、`4724792`；评分修正为 `ae3b57b`、`69b635a`。
`scripts/summarize_tool_efficiency.py` 可离线复算，使用 `--out` 指定新的结果文件。

前端“评测进展”页可逐条回放三组原始答案、调用参数、命中文档和共同 v5 评分；
v5 明确拆开指标名称，旧 v4 对照文件与原始答案继续保留，成绩不变。
例如 `pp-no-difference` 的首轮结果缺少政策检索，并错误地用签收日起算价保；
修正后的结果按下单日计算。点击“体验此用例”会切换对应模拟用户，发送后运行当前 Agent。
历史回放与实时体验分别展示，避免把保存的成绩当成当前每次运行的保证。

**可以讲清楚的经验。** 先从轨迹找到多查了什么，再修改工具信息边界。
优化出现回退时，沿失败样本检查缺了哪项证据，补回必要查询；用相同事实与评分口径
复测，同时披露没有改善的指标。这比只增加组件更能解释项目中实际解决了什么问题。

## 5. 可见用例达到 100%，换问题后还能成立吗？

**遇到的问题。** 35 条用例一直参与开发，提示词反复调整后的高分没有独立验证。
另有两个用户和多个商品覆盖不足，多轮历史虽然已支持，却没有在线会话评测。

**解决步骤。**

1. 在改变 Agent 行为前冻结独立的 15 条新增验证，用 14 个原集未使用的订单与不同问题角度；
   首次只跑一遍，保留失败和服务错误。用例作者已读过项目，不能称为严格盲测。
2. 在隔离进程中逐项删除四个提示词子句，同时做一次原提示词复跑；正式提示词不修改。
3. 冻结原 35 条定义，扩成 70 条公开开发用例：USER001 / USER002 / USER003 为
   38 / 15 / 17 条，P001–P004 均超过 3 条，待发货与取消订单各覆盖 5 条，
   54/70 条指定禁止工具，含 10 条多轮会话和 4 条库外问题。
4. 同一会话保留历史，每轮单独判定，任何一轮失败都不能被最后一轮的正确答案遮盖；
   汇总全会话请求消耗与错误。重要政策另检查支撑答案的小节，保存每次检索排名。

| 新增验证实验（各 15 条、1 遍） | 规则通过 | 严格通过 | 含执行错误的尝试 |
| --- | ---: | ---: | ---: |
| 冻结后的首次运行 | 11/15 | 10/15 | 1 |
| 不改提示词的复跑对照 | 12/15 | 11/15 | 0 |
| 删除“订单只查订单”子句 | 13/15 | 12/15 | 0 |
| 删除“物流调用范围”子句 | 11/15 | 11/15 | 0 |
| 删除“退货价保必须查政策”子句 | 13/15 | 12/15 | 0 |
| 删除“完整问题检索”子句 | 13/15 | 12/15 | 0 |

首次失败包括状态问题多查物流、价保漏查政策，以及一次 embedding 异常；
异常用例最终答对，但仍判失败，不剔除。价保答案还触发了狭窄的同义表达规则。
单次 15 条样本、服务波动和调用预算不能支持“低于 80% 就证明主要过拟合”的结论，
也不能据“删除后分数不降”认定某条安全规则只是记忆题目。正式规则本轮全部保留。
能够确认的是：旧 100% 没有代表新问题的表现，后续需要独立来源与重复验证。
这些问题现在已经公开，后续不再称为未见留出集。

证据：[首次原始记录](../results/holdout/first/per_case.jsonl)、
[不改提示词的复跑](../results/holdout/control_repeat/summary.json)、
[四项消融](../results/holdout/ablation/)、
[70 条开发用例](../data/eval/development.yaml)。
指标拆分与多轮实现为 `d24c653`、`b254db7`，扩集为 `f6cd51e`。
新增用例没有要求修改主提示词；检索改进使用公开开发查询，不能再充当独立验证。

## 6. 旧索引会返回过期政策，库外问题也总能“命中”

**遇到的问题。** 源文档从“7 天”改成“30 天”后，原索引仍可加载并返回旧政策。
另外，只要问题非空，FAISS 就会给出前三名；相似不等于有答案，`found=true` 因此失真。

**解决步骤。**

1. 用临时文档复现过期政策，再对源文件内容、切分配置与版本记录指纹；加载和内存检索
   均校验，构建期间文档变化也拒绝写入。纯标题小节不入索引，保留其他 chunk ID。
2. 先冻结 30 条真实检索采样问题，观察模型分数后标定；标定绑定模型、知识内容和切分版本。
3. 首版单阈值使开发集库外拒答达到 4/4，但误拒 P002 的 LDAC、佩戴调节与 P004 的
   金属物品问题。总分上涨掩盖了正向检索回退，保留这个版本，继续检查有效问题。
4. 在商品段落的 embedding 标题保留型号编号，补入公开开发集实际检索 query 与 SKU 库外反例。
   正反样本分数仍重叠，因此较弱分数直接拒绝，重叠区间按候选正文核验证据，强分数保留。
   核验只发生在该区间，用同一请求账本记录 `kb_relevance`，不作为评测的主评分器。

| 可复现检查 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 修改源文档后仍返回旧政策 | 是 | 明确拒绝并要求重建 |
| 纯标题小节 | 3 | 0 |
| 索引小节数 / 文档数 | 51 / 8 | 48 / 8 |

证据：[过期索引复现前](../results/rag_integrity/before.json)、
[修复后](../results/rag_integrity/after.json)。这两个探针为离线验证，不能证明真实语义排序。
指纹修复为 `afcb6ad`；修正误拒并保存证据为 `db238d6`。

真实 API 的固定采样复测共 81 个问题（原 30 条与新增 51 条）：
58 条库内有依据的问题保留 57 条，23 条库外全部拒绝；独立于边界选择的 validation
子集为 10 条有效、6 条库外，均符合预期。首版新增的三条误拒已恢复。
剩下一条 P002 快充问题的正确段落没有进入前三名，在未过滤的基线中也已漏命中；
拒绝错误候选不能代替找回正确证据。样本规模小，强分数也未必相关，不能当作通用阈值。

采样复测触发 3 次批量 embedding 和 6 次证据核验，共 9 次请求、3539 token；
核验 LLM 已定价小计 0.002778 元，embedding 未定价，不能称为完整成本。
离线探针也验证 2 次 Agent 请求 + 1 次检索 + 1 次核验全部计入，367 token 无遗漏。
证据：[原分布](../results/relevance/calibration.json)、
[型号编号与重叠分布](../results/relevance/with_identifiers.json)、

## 7. 正确证据在候选中，却没有进入最终上下文

**遇到的问题。** P002 快充回答没有找到“充电 5 分钟使用约 4 小时”；P003 温度问题
拿到包装清单；一般退货期限只覆盖七天无理由条款，遗漏十五天质量问题条件。
上一轮只记录累计文档命中，难以区分同一文档中找错章节与正确证据被过滤。

**根因与定位。** 先冻结 52 条章节级问题，逐次保存候选、前三名、核验后三个阶段。
32 条开发问题中，Dense 的 Recall@10 为 100%，排序 Recall@3 为 81.2%，核验后
为 77.1%。快充、温度正确章节分别排第 9、第 10；主要缺口是排序，不能笼统归为
“知识库没数据”。旧 cosine 门槛还误拒了已有有效候选的金属物品问题。

**解决步骤。**

1. 根据正文标注每个问题必须覆盖的事实及其充分章节，允许同一事实由不同章节支持。
   普通退货与质量退货要求分别覆盖，不能只命中 `return_policy` 就判成功。
   32 条开发与 20 条验证的标签、语料和条件在首次运行前冻结，不删掉检索失败问题。
2. 使用中文搜索分词建立 BM25，保留 `P002`、`USB-C1`、`LDAC` 和数值单位。
   BM25 与 Dense 共用已有 48 个章节，不改变 embedding 输入和索引版本。
3. 加入 RRF 按名次融合并按 chunk ID 去重，保留各路原始分数与排名。
   Dense 的 cosine 标定继续保留；BM25/RRF 候选按正文核验，避免将不同尺度的分数
   套进旧阈值。核验纳入同一个请求账本。
4. 先比较开发结果并记录部署选择，再运行冻结验证；前端展示相同原始证据，
   校验用例、语料与原始记录 hash，支持失败用例回放。

当前部署选择 **BM25＋正文证据核验**，选择发生在验证运行前。RRF 找回快充、温度等
缺口，但一般退货期限仍只覆盖一种条件；BM25 当前覆盖更好并省掉查询 embedding。
全部候选 Recall@10 已很高，未来如果扩充语料后前三名排序再次成为瓶颈，可据此验证
reranker。多轮指代需另测 query rewrite，本轮没有实现独立改写模块。

**代价与边界。** 开发集 Dense 核验 4 次、1840 token；BM25/RRF 各核验 32 次，

实测值，不包含回答生成；单遍合成语料不能证明端到端正确率、完整成本或泛化改善。
本次没有删除失败问题、调整标签或修改主提示词来提高成绩。
