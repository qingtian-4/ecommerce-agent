# 评测集原始方案（Eval Plan）

**状态（2026-10-09）**：原 35 条历史用例冻结保留；新增验证集 15 条、公开开发集 70 条，
其中 10 条多轮会话逐轮评分。下文保留最初的设计背景与估算，
实际口径以 `data/eval/development.yaml`、`src/acs/eval_runner.py` 为准；
后续修复与实测结果见 [主要问题与解决过程](PROBLEM_SOLVING.md)。

**目标不是"做一个 benchmark"**，而是把「改进了多少」从主观判断变成可测量的数字。
当前项目只有 4 条手写 case，6 个已观测缺陷里有 3 个**无法判断严重程度**，因为只有单次观测。
这份方案就是为了消掉那 3 个"无法判断"。

---

## 0. 一句话结论

**约 34 条用例，跑 3 遍，不改任何生产代码，两天内可完成。**
重点不在于条目多，而在于**每条用例都声明"必须调什么"和"绝不能调什么"**——
后者是唯一能不依赖 judge 就测出「无效工具调用」的手段。

---

## 1. 为什么是现在这个规模，而不是 100 条

| 方案 | 条目 | 能回答的问题 | 成本 |
|---|---|---|---|
| 现状 | 4 | 能不能跑通 | — |
| **本方案** | **~34** | 改动了之后，哪一项变好、哪一项变差 | **≈ ¥0.3 / 6 分钟** |
| 完整集（后期） | 120+ | 统计显著性、置信区间 | ≈ ¥1 / 20 分钟 |

34 条不是"缩水版"，而是**先验证测量管线本身是否正确**。
早期调研的教训值得复用：*数据集往往是真的，跑偏的是指标计算代码*。
所以这一轮的交付物是**可信的测量管线**，不是漂亮的数字。

## 3. 用例 schema

```yaml
- id: k-return-window-in
  category: rag+tool              # 用于分组统计
  user: USER001
  query: "订单 O10024 是我前天收到的耳机，现在还能退吗？"

  # ---- 路由与工具（考 Agent 的决策）----
  required_tools: [get_order, search_knowledge]
  forbidden_tools: [get_logistics, get_price_history, get_product]
  required_tool_args:             # 只校验关键参数，不校验全部，避免过拟合
    get_order: {order_id: "O10024"}
  expected_stop_reason: answered

  # ---- 检索（考 RAG）----
  required_documents: [return_policy]

  # ---- 生成（考回答质量，规则判定）----
  must_contain: ["7 天"]
  must_not_contain: ["不行", "无法退货", "15 天无理由"]
  # ↑ "15 天无理由" 是故意设的诱饵：文档里 15 天是"质量问题退货"，
  #   把两者混为一谈是最可能的事实性错误

  # ---- 溯源 ----
  source: database                # database | kb | handwritten
  notes: "签收 1 天前；within_return_window=True"
```

### 三个字段的设计理由

| 字段 | 来自哪个仓库的启发 | 作用 |
|---|---|---|
| `forbidden_tools` | `dxl-commerce-agent`（唯一有此设计的仓库） | 直接测「无效工具调用」。问候语调 `order_lookup` 就是失败 |
| `required_documents` | τ²-bench 每个 knowledge 任务都带 | 让检索**逐条客观可判**，不需要 judge |
| `required_tool_args` | `zhiwei` 的 `expected_tool_params` | 把"选对工具"与"填对参数"分开计分 |

## 4. 指标：怎么算、数据从哪来

**重要约束（本阶段）**：所有工具都是只读，**没有数据库状态变化可查**。
所以"最终状态正确性"这类指标本阶段缺席——它需要写工具（退货申请等）。
这一点必须写在报告里，不能假装测过。

### 4.1 完全由 trace 推导，零额外成本

| 指标 | 适用条件 | 判定 |
|---|---|---|
| **工具选择准确率** | 所有用例 | `set(实际) == set(required_tools)` |
| **无效工具调用率** | 所有用例 | `set(实际) ∩ forbidden_tools ≠ ∅` 即失败 |
| **必填工具召回率** | `required_tools` 非空 | `required ⊆ 实际` |
| **参数准确率** | 声明了 `required_tool_args` | 每个键值都匹配 |
| **冗余调用数** | 所有用例 | `len(实际) - len(required)`，取平均 |
| **工具调用次序** | 所有用例 | 实际序列 vs `required_tools` 顺序是否一致（**当前已知不稳定**，此项专门量化它） |
| **停因正确率** | 声明了 `expected_stop_reason` | `stop_reason` 是否匹配 |
| **错误率** | 所有用例 | `errors` 是否为空、按 `error_type` 分类 |
| **P50 / P95 延迟** | 所有用例 | 实测，**按 category 分组**而非只报总体 |
| **平均 token / 成本** | 所有用例 | 来自 `totals` |

### 4.2 检索指标（`required_documents` 非空，约 17 条）

| 指标 | 判定 | 备注 |
|---|---|---|
| **Recall@3** | `required_documents ⊆ {命中 chunk 的 document_id}` | 与 `top_k=3` 对齐 |
| **MRR** | 首个必需文档所在名次的倒数 | 量化"排在后面"的严重程度 |
| **有效命中数** | 命中的 chunk 里，属于必需文档的条数 / 3 | **正对当前缺陷**：Case 1/3 的 top-3 有 1 条是标题-only chunk，有效信息只有 2 条 |

**局限必须写明**：这一层测的是"必需文档**被召回**"，不是"**被用于回答**"。
要测后者，需要在工具返回里回溯最终答案的出处——本阶段不做，列为已知缺口。

### 4.3 生成指标（规则优先，约 20 条）

| 指标 | 判定 |
|---|---|
| **must_contain 命中率** | 按关键词/事实点逐条算 |
| **must_not_contain 违反率** | 命中即失败，**这是幻觉率的代理指标** |
| **答案非空率** | 极端兜底检测 |

**为什么只用规则、不上 LLM judge**：34 条、事实点明确，`must_contain` 就够用；
引入 judge 会新增一个随机源，还要先人工校准 judge，成本不成比例。
LLM judge 留到需要评"回答是否自然/完整"的时候。

### 4.4 稳定性指标

每条用例跑 **3 遍**，计算：

- **pass^k**（k=3）：同一条 3 次**全部**成功的比例——沿用 ECom-Bench 与 τ² 的定义
  （与 `pass@k` 不同：后者只要 1 次成功）
- **翻转率**：3 次结果不一致的用例占比

**为什么必须要这一项**：当前已观测到 Case 2 的工具调用顺序在不同次运行间不定。
`temperature=0` 并不保证 API 层面完全确定，所以"稳定性"必须实测而不是假设。
这也正好回答了"只有单次观测，波动未知"这个缺陷。

## 5. 成功判据（任务成功率）

一条用例算"成功"需要**同时**满足：

```
1. required_tools ⊆ 实际调用的工具        （该调的都调了）
2. 实际 ∩ forbidden_tools = ∅            （不该调的没调）
3. required_tool_args 全部匹配            （参数对）
4. stop_reason == expected                （正常收口，没超步数）
5. must_contain 全部出现                  （说到了要点）
6. must_not_contain 全部未出现            （没胡说）
```

**为什么是合取而不是加权**：加权分看不出坏在哪。
ECom-Bench 用 `action × search × output` 相乘，导致 0 分无法归因——这是我们明确不采纳的。
**但每个分项都要单独报告**，这样"失败原因分布"才有意义。

## 7. 成本与耗时估算（基于 E001 实测）

| 项 | 计算 | 结果 |
|---|---|---|
| 用例数 × passes | 34 × 3 | 102 次会话 |
| 每次会话的 LLM 调用 | ~2 次（判断是否用工具 + 生成；多跳更多） | ~250 次调用 |
| 单次调用成本 | ¥0.000229（E001 实测，thinking 关闭） | — |
| **LLM 成本** | ≈ 250 × ¥0.000229 | **≈ ¥0.06** |
| Embedding 成本 | 每条检索 1 次；SiliconFlow 计费低 | 可忽略 |
| 单次会话延迟 | ~1.8 s（E001 实测） | — |
| **总耗时** | 102 × 2 s | **≈ 4 分钟** |

即使实际调用数是估算的 3 倍，也仍在 **¥0.2 / 6 分钟**量级。
**成本不构成约束**——所以不要为了省钱而削减条目或 passes。

## 8. 执行顺序（关键：先冻结，再优化）

```
① 写 34 条用例           → 人工 review 一遍（约 1 小时）
② 实现 eval_runner       → 不改生产代码
③ 冻结 v1 基线            → 跑 3 passes，记录 commit + 用例版本 + 索引版本
④ 看失败分布              → 按 category 与失败类型分组
⑤ 选 1~2 个改进点         → 从失败分布里选，不从设计文档里选
⑥ 改一处，重跑，对比       → 记录 delta（效果、延迟、token、成本）
```

**③ 的"冻结"是纪律，不是形式**：
必须记录 `commit`、`cases.yaml` 的 hash、`kb_meta.json` 里的索引版本。
否则改了知识库文档后，"上周 85% 这周 79%" 无法归因——
这是 E000 已经写进 `EXPERIMENT_LOG` 的风险项。

## 9. 必须先说明的一个顺序问题

我原本把「修检索缺陷」排在第 2 位。**现在认为应该换一下顺序**：

```
先建评测集（本方案）→ 再修检索
```

**理由**：

| 顺序 | 会发生什么 |
|---|---|
| 先修检索 | 我知道"标题-only chunk 占了 top-k"，但**不知道它影响了多少条、多少比例**。修完只能说"感觉变好了" |
| **先建评测集** | 跑出基线后，`Recall@3` 与「有效命中数」会**直接显示**这个缺陷的规模；修完有 delta 可对比 |

而且这正好构成一个完整、可验证的故事：
**基线 → 评测 → 发现瓶颈 → 改进 → 复测**——而不是"我加了个模块"。

## 10. 这份方案的已知局限（必须写进报告）

1. **34 条不足以谈统计显著性**。95% 置信区间会很宽。定位是"可测量的最小集"，不是 benchmark。
2. **没有数据库状态校验**（无写工具）。"Agent 是否真的完成了操作"本阶段测不了。
3. **检索只测"被召回"，不测"被使用"**。
4. **`must_contain` 是关键词匹配**，同义表达会误判为失败（假阴性）。
   缓解：`must_contain` 只放**确定的数字与关键实体**（"7 天"、"O10024"），不放宽泛说法。
5. **用例是手写的**，不是从真实对话分布采样，可能系统性偏离真实用户问法。
6. **只覆盖中文、单一品类**（耳机 + 充电配件）。
