实现订单定位、草稿更正、预览确认、幂等申请及独立认证审核的完整售后 Demo。

## 三个值得讲的 Badcase

### A. 查询过订单，草稿却四轮没有保存

原始`orders-02 / trial=1`用户说“我想退 S20017。”。`get_order`返回本人订单，模型持续追问
商品明细，却没有调用`update_return_task`。Loop 把无工具回答当成 answered，ChatService 随即
完成会话；模型提到订单不代表数据已经落库。SQLite 原本允许只知道订单、不知道商品的草稿，
缺的是结束时的受限状态完整性检查，不是新的 Memory 表。

比较过提示加强与后端检查。最终只在明确当前用户原话、同轮成功查本人订单、无既有草稿、
未超预算且正常结束时补订单；`only_if_absent`在 SQLite 写事务内区分新增、已满足、冲突和失败。
不自动选择 item、reason 或创建申请，不覆盖已有任务，不重复增加 revision。写后重新读回，
同步任务卡、AgentResult、assistant message 与 final Trace，失败不报完成。

红绿与 8 组固定模型配对见[P0 报告](../results/p0_order_draft_integrity/REPORT.md)，
原始轨迹见[历史 raw](../results/iteration_v2_recovery/local_after/raw.jsonl)。
8 组是固定决策工程对照，不是 8 组真实模型成功率。补存加读回预热 p95 约 240.26ms，不能承诺 20ms；
默认关闭、只覆盖有限授权表达。这个例子适合解释“模型流程结束”和“业务状态完整”为什么不同。

### B. 白色要求在上下文里，模型仍推荐黑色

较早真实实验中，恢复后的请求确实包含“后续一直只看白色耳机”，且工具返回 SKU 齐全，
模型仍推荐黑色。原 P1 只纠正首轮纯候选，遇历史会话主动退出；因此不能归因 Memory 丢失。
另有跨订单 S20008 白色被说黑、S20003 黑色正确的绑定问题。事实正确与执行用户约束是两个层次。

方案上没有增加上下文、再调一次审查模型或新 Fact Ledger；复用 SQLite 中本人用户原话，
折叠有限颜色状态，明确更正覆盖、取消清除、未知条件暂停，再按同轮完整工具结果过滤候选。
商品属性始终跟随订单/明细/SKU，不让模型拼接。发现最终纠正仍暴露流式错误后，在可识别
保护请求中先缓冲模型结论，允许展示工具进度，核验后同步终态和历史。

最新真实样本中，三类有效颜色限制末轮关闭 0/3、开启 3/3；白色恢复和跨单插问的候选原答
仍有黑色，最终被同次确定性纠正。黑色更正开启组原答本来已基本正确，不能将全部组间
差异归因过滤。原始请求和复核见[最新 raw 与 analysis](../results/final_delivery_c9afdbf/live/analysis.json)，
此前失败见[早期真实报告](../results/p1_live_20261021/REPORT.md)。

局限是有限表达漏接管、复杂混合对象会退出；自由附注仍可能错。门控也使目标首字中位数
观察增加约 1123ms。三组单次不是总体遵守率，更不能承诺所有页面文字都有通用事实验证。

### C. 工具返回正确，模型把明细数算成件数

本店 USER001 为 20 笔订单、25 条商品明细，`quantity`合计 29 件。较早模型分别答 25 和 26 件，
最新关闭组答 27 件；同轮 list_orders 数据没有丢失，错误在单位理解、聚合和最终生成。
不能只检查“调用过订单工具”，也不能把每条明细当一件。

比较 Prompt 解释单位、额外 SQL 工具与已有结果确定性聚合。选最小方案：复用单次完整
list_orders，在 Runtime 分别计算`len(orders)`、明细条数和`sum(quantity)`；支持首轮明确
状态或订单子集，型号数、金额及历史隐含范围不接管。统一拒绝 count 不符、重复 ID、
异常嵌套和不可信部分结果，避免对残缺数据报权威总数。

最新三个统计任务关闭 1/3、开启 3/3。开启组原模型仍答 26 件、20/23/26 和签收 8/9/12，
最终分别为 29、20/25/29、8/10/14，三例同次错误原答均被纠正。
[精确值与原答](../results/final_delivery_c9afdbf/live/analysis.json)可复查，无新增模型调用或业务写入。
本轮仅首轮显式范围，不能讲成任意自然语言 BI，也不把数量聚合当通用推理能力提升。

## 两分钟架构讲解稿

我做的是一个可恢复的电商售后 Agent，重点解决“模型说得像完成了，但业务其实没完成”
以及“工具查对了，最后答案仍然错”的问题。

客户页面和离线评测共用 ChatService。它负责用户身份、SQLite 会话、排队和整轮预算，
下面是手写的 Function Calling 循环，模型选择知识或业务工具，工具负责执行和返回证据。
政策规格来自版本化文档，订单、SKU、数量和申请状态来自 SQL。模型没有正式提交和审核权限，
预览之后必须由页面确认，ReturnService 在事务里核验状态、数量和幂等，管理员单独认证。

我通过失败轨迹做过三个修复：明确订单但漏调草稿工具，用受限结束检查补存；跨轮白色限制
还在上下文却被忽略，用已存用户原话和同轮事实做有限过滤；订单数、明细数、件数混淆，
直接按结构化结果计算。保护请求在核验前不展示模型结论，原答留在诊断 Trace。

评价分本地业务、真实模型和官方 Benchmark。最新 11 个已见题每臂一次为 6/11 到 11/11，
五个错误原答同次被纠正，但样本太小，不能说总体成功率提升。此前完整τ零售 684 段用于
比较 Loop，保留官方数据和评分，不验证本店页面。项目已能完整演示并复现测试，默认保护仍关闭，
当前是实习工程 Demo，不是生产客服。

## 五分钟架构讲解稿

**0:00 至 0:45，业务目标。** 页面展示商品政策与订单查询、退货草稿、预览确认、管理员审核和
结果查询。我把范围限定为准备并管理售后申请，没有真实退款、换货或人工接管。数据是合成的，
客户身份为模拟用户，避免把演示系统包装成生产账户系统。

**0:45 至 1:40，执行路径。** 请求先进入 ChatService，读取本人会话和任务，再在上下文字符
预算内按完整轮次裁剪历史，身份不由模型决定。模型通过自定义 Loop 选择工具，ToolRegistry
检查参数并注入用户身份；每次工具调用、回执、错误和 usage 都有 Trace。RAG 提供知识，SQL
提供当前业务事实，不能拿旧模型答案当当前资格。支持 BM25、向量、RRF 及可选重排，Demo
为降低准备成本默认选择整篇文档模式，不能把它说成向量 RAG 现场展示。

**1:40 至 2:30，业务状态。** SessionStore 存完整会话和带来源/revision 的草稿。换订单或明细时
清除依赖的旧字段及旧预览；没有完整材料就继续问。页面预览生成绑定内容、政策和状态的快照，
确认入口在事务中重新核验并保证幂等。审核权限来自认证请求，终态不随意改判。这里的关键
不是 Prompt 劝模型别越权，而是后端根本不给模型正式提交和审核能力。

**2:30 至 3:40，三个失败及最小修复。** 一个模型查到 S20017 却四轮不保存草稿，我没有建新记忆
平台，而是结束时按严格授权和同轮回执做 only-if-absent 检查。另一个模型明知白色限制仍列黑色，
证明“上下文里有”不等于“约束会执行”；有限用户约束从原话重建并在完整候选上过滤。
数量问题也不是 SQL 错，而是把 25 条明细当件数，Runtime 直接计算 20 单 25 明细 29 件。
后来发现最后纠正不能阻止用户先看见错误，所以只为可识别保护请求门控正文，不取消全部流式。

**3:40 至 4:35，怎么评价。** 工具优化历史 35 题各 3 次从 160 调用到 122，少 23.8%，但平均 Token
多 4.2%；多轮历史前后 140/160 没有提升，必须如实保留。完整τ零售 114 题各 3 次两组 684 段，
项目 pass^1 为 86.5%、官方同模型 87.4%，没有说跑赢官方。最新真实 11 题一次对照 6/11 到 11/11，
五个错误原答同次纠正，58 请求估算 0.143 元。所有数据都有冻结条件、原始 usage 和失败，
语义复核未经独立外部盲审，不把编码助手的判断说成客户成功率。

**4:35 至 5:00，交付与不足。** 页面脚本注错跑通确认、审核、恢复和安全边界，离线 695 项通过，
无密钥 CI 执行锁定依赖测试。四个保护默认关闭，有限同义表达、自由附注和统计隐含范围仍可能错，
首字等待也变长。我会停止扩展框架，进入维护与面试准备；新增覆盖必须先定义正反例和预算。

## 面试追问与参考答案

### 1. 为什么手写 Loop，不用 LangGraph？

本项目主要是有限工具循环加状态化业务，现有 Loop 已覆盖调用配对、预算、Trace 和恢复，
真实缺陷没有证明需要迁移框架。手写便于定位模型决策与后端执行的边界；代价是调度与恢复
需要自己维护。不是说框架无用，复杂分支和长期任务超出现有范围时才重新评估。

### 2. Function Calling 怎样保证调用正确？

Schema 只帮助模型生成参数，不是安全证明。ToolRegistry 解析、校验并剥离模型身份参数，
应用绑定用户/会话/轮次，数据层强制归属；业务写入再经过事务和状态检查。工具成功也不等于
最终回答正确，因此另有事实绑定和答案评测。

### 3. 怎样处理工具调用和结果不配对？

Loop 记录每次调用 ID 并返回对应结果，包括拒绝执行的预算内错误结果；完成消息保存前检查
消息序列。中断不能把半个工具组当完成，终态显式标记未完成。可打开
[test_turn_budget.py](../tests/test_turn_budget.py)解释拒绝过量工具仍补全配对的测试。

### 4. 为什么同时需要 RAG 和 SQL 工具？

政策规格是版本化文档，检索适合定位知识；订单归属、数量、日期和执行结果必须读业务事实。
把订单埋入知识检索会弱化权限和实时性，把政策交给模型记忆又会失去来源和版本。查询日期
初筛不代替完整资格；预览与提交仍用同源业务政策复核。

### 5. 为什么 BM25 可以作为默认？

知识库很小且有明确商品/政策词，BM25 是可解释的简单基线。项目做了 Dense、RRF、可选重排
和证据核验对照，不能因为更复杂就默认更好；必须同时看命中、拒答、误召回、调用和延迟。
Demo 整篇文档模式又是另一个实验选择，不是 BM25 或 Embedding 已被废弃。

### 6. 重排一定能提高质量吗？

不一定，重排只排序候选，不保证支持最终结论。项目的重排/补位实验保存了覆盖和核验成本，
补位会明显增加核验 Token。没有相同问题、候选预算、下游判据和全部失败记录，不能用单个
漂亮例子证明值得默认开启。见[检索实验](EXPERIMENT_LOG.md#e005--api-重排与核验后补位)。

### 7. 怎么避免索引过期或不匹配？

记录知识正文、切分和 Embedding 输入等版本/指纹，加载和评测时校验，不静默使用不匹配索引。
切分变化要重建并重新标定相关性。版本一致是可复现前提，不能因为检索返回了内容就认为来源正确。

### 8. “用户约束在历史里”为什么还是会失败？

上下文可见不代表模型会执行。原始请求证实白色限制未被裁剪，SKU 也正确，模型仍给黑色候选。
因此先区分输入缺失和决策执行，再做有限后端过滤；本项目没有用扩大 Memory 来掩盖问题。
未知更正会暂停保护，避免错误固化旧限制。

### 9. Context Engineering 做了什么，没有做什么？

按完整轮次组织消息，保留必要系统信息和当前草稿，限制输入字符预算，重新查询当前业务状态。
字符不是 Token，最终渲染表格也可能增大下一轮输入。没有通用压缩记忆、Fact Ledger 或学习型
上下文选择器；本轮不重构上下文，只报告实际请求和潜在后续字符变化。

### 10. 为什么草稿状态不能只存在模型对话里？

模型文字不是可执行业务状态。SQLite 草稿能记录字段来源、revision、归属和更正失效规则，
重启后可恢复，也能让预览/确认依赖明确状态。P0 补存仍必须有当前用户授权与成功订单回执，
模型提到一个订单号绝不能自动创建草稿。

### 11. 幂等与事务分别解决什么？

事务让一次确认中的状态核验、数量占用和申请写入一起成功或回滚；幂等使重试不会重复创建。
只用事务可能产生两笔分别成功的重复请求，只用幂等键又不能保证业务约束原子成立。
预览过期、业务变化和并发提交仍须在写事务中核查。

### 12. 用户说“取消”为什么不直接执行？

“不是要取消”“如果取消”“暂停”不等于授权清空。取消工具使用当前原话明确授权，在事务内
判断，复杂表达保守拒绝并请明确确认。已提交申请不能通过取消草稿撤销；模型误调工具也应被后端阻止。
这是一条有限破坏性操作协议，不能宣称理解任意自然语言。

### 13. 为何最终回答纠正还不够？

流式页面可能先显示错误，最终正确不能撤回用户看过的文字。受保护请求先缓冲结论，工具进度
正常展示，完整回执核验后再同步 answer、历史、Trace 和持久状态。代价是首字延迟增加，
普通未受保护问答继续流式；必须逐帧验收，不能只检查最终字符串。

### 14. 工具返回损坏或只有一部分怎么办？

共同校验包络、count、唯一 ID、嵌套结构与部分结果标记；三种渲染都拒绝同类坏结果。
没有可靠完整数据就不报完整候选或总计，给未核实提示，不自动补查或写业务。
空结果与坏结果不同，空列表 count=0 可以产生明确空结果。

### 15. 为什么不让模型自己算订单数量？

明细条数与 quantity 合计是明确的数据聚合，确定性代码更可靠且无需模型调用。模型负责理解
可支持的请求范围，Runtime 按订单/明细/件数计算；型号数、金额和隐含历史范围本轮退出。
不把数据库已能精确计算的问题包装成模型推理挑战。

### 16. τ²-bench 到底测了什么，为什么商品不同也能跑？

它包含任务、模拟环境数据、政策工具、用户模拟器和官方评分，既不只是问答数据集，也不是
本店订单替换。项目适配 Loop 到官方零售环境，保留扫地机器人等官方商品与任务，测遵循政策和
调用工具的能力。它不验证本店 RAG、权限、确认页面或管理员审核，两个层次必须分别报告。

### 17. pass^1 和 pass^3 怎样解释？

本实验 pass^1 是全部重复尝试的平均成功，pass^3 是每题三次均成功的题目比例，强调稳定完成，
不是“试三次至少对一次”的 pass@3。114 题、每臂 342 段；项目 pass^1 比官方略低而 pass^3 略高，
不据此宣称总体优胜，内部预算不完全一致也需要披露。

### 18. 6/11 到 11/11 是否证明提升？

它支持 11 个已见固定任务的局部结果，五个同次错误原答被纠正是更直接的机制内证据。
每臂一次、无独立盲审、模型别名和缓存存在波动，不能估计总体成功率或稳定因果效应。
两机制按任务子集有观察，但没有做四臂析因；共同 P1 和安全修复的贡献不能从这批单独分离。

### 19. 裁判误判或 JSON 坏了怎么报告？

保存原始文本、解析对象、异常类型/原因、版本和 system 哈希，单列 unjudged 而不是当成已证实
业务失败。同用户跨会话不等于越权，成功工具预览也不因没有 UI 脚本动作而被否认。
历史旧分保留，新校准不冒充 Agent 能力提升；新语义裁判尚无付费复验，明确写未验证。

### 20. 你如何控制成本，下一步还缺什么？

在线前冻结 11 题、做无网络预演，逐请求预留输入与最大输出费用且不依赖缓存优惠，记录所有
真实 usage 和尝试；余额不足下一完整批次就停止，不挑题重试。58 请求估算 0.143 元，保守账本
0.879 元不是实付。工程上还缺更广表达验证、生产客户认证/运维和通用事实保护；当前停止扩展，
只维护实习 Demo，不能给生产 SLA。
