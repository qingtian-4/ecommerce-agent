## 1. 推荐定位与业务终点

面向单店的电商客服 Agent：依据版本化知识与业务数据回答咨询，
在多轮对话中定位订单、保存及更正退货信息，经页面明确确认创建待审核申请，
由独立管理员审核，客户能够查询真实结果。通过失败取证、最小修复和同条件评测
持续改进可靠性与效率，形成可以部署、演示、复现和解释的工程项目。

沿用既有面向 Agent 应用开发实习的工程目标。当前先做好单进程、合成数据下的
完整流程；真实客户分布上的泛化仍需额外证据，不将其写成线上产品成绩。

主线终点为：**申请经审核通过或拒绝，结果真实可查**。审核通过表示允许退货，
不表示仓库已收货、退款已执行或资金到账。

| 范围 | 当前边界 | 后续投入条件 |
| --- | --- | --- |
| 商品、政策、订单、物流、价保咨询 | 保留；明确无匹配、未知与权限边界 | 从错误回答、漏查或无效调用定位改动 |
| 无理由与质量问题退货 | 订单明细与数量粒度；单份草稿对应一项明细 | 优先改进更正、暂停恢复和对象绑定 |
| 预览、确认、创建申请、审核与查询 | 使用实际后台处理器；模型不拥有提交或审核权限 | 继续验证过期确认、重复提交、数量与角色约束 |
| 多项诉求 | 先覆盖退货途中插问订单/物流后恢复的行为 | 复现遗漏或串单后再扩展状态；不直接建设通用任务平台 |
| 质量凭证 | 接收、保存、关联与供审核查看 | 自动识图需单独的失败案例、数据和评测依据 |
| 运行与展示 | Python、手写 Loop、SQLite、Gradio、单进程容器 | 当前不增加服务、框架或基础设施依赖 |
| 质量与效率验证 | 本地任务评测为主，外部零售 Benchmark 为辅 | 改进必须有同样本、同条件的前后证据 |

## 2. 当前不纳入交付范围

- 真实支付退款、仓库验收、物流履约及真实商业系统接入。
- 取消/修改订单、修改地址、实际换货和价保申请；τ 环境支持这些动作不构成本地扩围理由。
- 通用人工工单、实时人工聊天与消息接管；现有管理员审核不等于人工客服已经接入。
- 客户账户认证、多店租户、跨机器高可用或高并发平台；模拟身份与后台归属校验继续保留。
- 智能硬件故障排障、语音、多语言与自动视觉诊断。
- SFT、LoRA、强化学习、运行时多 Agent、自动改代码或无审核发布。
- 为覆盖外部所有领域而增加航空、电信、银行业务，或把排行榜分数作为产品目标。

这些是当前边界，后续扩围需要具体业务问题及独立验收，不代表永久放弃。

## 3. 三部分各承担什么

```text
本店知识与业务数据 → 本地应用 → 本地状态、答案、恢复与交互评测
                              ↑
                    经失败证据支持的修复
                              ↑
Anker 工单/实现 → 表达与机制参考；改写为本地事实下的开发案例

项目 Agent Loop → 适配器 → τ 官方环境、工具、用户模拟器与原版评分
```

三部分分别报告，不合并成一个“整体准确率”。外部适配复用实际 Loop，替换为官方
政策和工具；本地完整应用评测仍走 ChatService、业务工具和真实后台操作。

## 4. τ2-bench 是什么

它既是 Benchmark，也包含公开任务数据和可执行的仿真评测框架。其组成包括领域
政策、商品/用户/订单等业务数据、工具实现、任务目标、用户模拟器、编排器和评分器。
用户模拟器根据私有任务说明与客服交互，被测 Agent 不能获得评分目标或参考答案。
它不是一组固定的问答对，也不要求将数据导入本店知识库。

原 τ² 论文的主要新增点是电信双控制环境：Agent 与用户都能通过工具改变共享环境，
评估沟通和协作。零售领域承接原 τ-bench 任务，与本项目最相关，优先使用。

仓库名称仍为 `tau2-bench`，当前首页已介绍 τ³。我们的已有实验固定提交
`dd8757d4c8791dad7b3cdaf02a105a3d5f9d86bd`、包版本 1.0.1，后续默认沿用此版本，
不把它称为原始 2025 τ² 论文配置；升级版本需要另建实验，不能直接拼接成绩。

### 数据与评分的实际核对

固定版本 retail 共有 114 个任务，`base` 为全部 114 个，`train` / `test` 为 74 / 40。
这里只评价 Agent，不训练，建议正式外部评测采用完整 `base`。公开任务与外部来源
不等于严格盲测；若对任务反复调优，须披露开发使用情况。

每个任务带用户情境、初始状态和 `evaluation_criteria`。参考 `actions` 通常用于
生成目标数据库终态，不要求复制唯一调用顺序；实际计分由该任务 `reward_basis`
决定。固定 retail 数据中 112 个任务使用 `[DB, NL_ASSERTION]`，另 2 个只使用 `[DB]`。
自然语言断言可能为空，评分通过也不等于完整语义、全部政策和每项过程约束均已验证。

特别注意：同版本说明文档概述的默认 `[DB, COMMUNICATE]` 不能代替任务文件中的
显式配置。后续报告须核对实际任务、评分实现和原始 `reward_breakdown`。
官方分数保持原口径；额外语义复核或违规检查另列，不修改原版总分。

建议报告平均 reward、任务成功比例、`pass^1`、`pass^3`、失败类别、调用、token、
耗时及成本完整性。`pass^3` 衡量连续三次都成功的可靠性，不是三次至少成功一次的
`pass@3`；重复数大于 3 时使用官方组合估计实现。
基础设施错误的纳入规则须预先冻结：保留官方指标及其分母，同时单列所有计划运行
的完成/失败数，不能静默丢弃异常或挑选重跑成绩。

### 我们已经做过什么

现有 `scripts/tau_acs_agent.py` 在实际 `CustomerServiceAgent.chat_stream` 工具调用处
暂停，把调用交给官方编排器执行，再将官方结果送回原 Loop。它不执行本地售后工具，
也不是只给官方 Agent 更换模型。领域提示使用官方政策，不携带本店页面确认规则。

已有固定任务 0–4 各 3 次：项目 Loop 14/15，三次均成功 4/5；官方 LLMAgent 同模型
对照 15/15，三次均成功 5/5。原始结果 hash 与汇总一致。
唯一失败为任务 4 第 1 次：DB=1，但将 10 个可选款式说成 11 个，NL_ASSERTION=0。
它验证了外部桥接可运行，样本覆盖不足以代表完整零售能力，也没有证明优于官方方案。

该适配不覆盖本地 RAG、ChatService、SQLite 权限、页面确认、管理员审核或浏览器。
现有 ACS 外部输入上限为 64,000 字符，本地为 24,000；官方对照没有同样的 ACS
内部预算。相同模型不等于完全相同执行约束，不能把差异都归因于 Loop 算法。
外部记录的 cost=0 源自上游未识别价格，不能称为免费或完整成本。

## 5. Anker 项目怎么结合

核对提交 `6ad5836c41d38b8f2d9f1509c19ce2d5f8559832`：已提交 63 封脱敏工单、
63 条工单标注、875 条 Q&A、16 笔订单和 10 张附件；原始资料包及大量运行明细
没有提交，不能据此声称能完整复现它的历史成绩。

优先参考：事实保留对象、肯定/否定、原话与修订；多诉求与业务对象绑定；
区分系统缺陷、知识缺口、等待用户及执行能力边界；从失败生成成对反例并同条件复测。
其“AI Native 自我迭代”是人参与验收、编码 Agent 修复与复测的工程流程，
自动训练和无审核发布不是已实现能力；服务质量闭环文档也有明确的设计提案边界。

我们已有 `return_tasks.sources`、修订失效、状态校验、执行轨迹和多轮评测，应在
这些基础上按失败补强，不另建一套重复账本或移植其 LangGraph/WeKnora 技术栈。
其售后政策和产品事实不混入本店知识。阅读过的案例用于开发参考；移植后的结果
标为本地改编评测，不称为 Anker 原版成绩或未见客户测试。

| S3 | P1 | 补本地否定/对象互换、更正、跨订单插问恢复、用户陈述与业务记录冲突案例 | 每类包含正例和易误用反例；事实从本店 KB/DB 推导；运行前冻结并按来源任务簇分组 |
| S4 | P1 | 根据 S2/S3 确认失败，修改 sessions、chat_service 或 Agent 输入组织 | 先复现再修复；相关案例及已有回归通过；禁止副作用约束无新增失败 |

| S6 | P1 | 分开呈现本地业务结果、τ 外部能力和改进前后证据 | 标明代码/数据/模型/预算/裁判版本、样本与重复数；失败可回放，不以测量修正冒充能力提升 |

S3 新案例在参与调优后转为回归材料；现有 80 段任务已经看到结果，继续保留为回归，
不重新命名为新留出。新的验证按来源簇隔离，不能只换订单号或把同一正反例拆到两组。

S5 的最小选项是继续保留现有 5 题作为集成冒烟；正式范围推荐完整 114 题，
避免便利子集覆盖过窄。执行前先完成评分配置、超时、预算差异和成本记录的静态审计，
冻结模型、用户模拟器、裁判、种子、任务 hash、通信模式和错误处理口径。
需能访问同一固定上游环境与现有模型服务；API 凭据仅供运行时使用，不写进清单。
684 段是对话数，不是 API 请求数；预算由已有真实轨迹估计，不给出未经测量的费用承诺。
本轮尚未恢复完整上游运行环境，也未验证供应商在线可用性。

本地应用验收继续覆盖正常提交、更正后旧确认失效、缺材料、取消/未签收订单、
越权、超量、重复/并发确认、响应丢失、断流及重启恢复。τ 环境中的口头确认和
模拟写操作按官方政策执行，不反向改变本店页面确认与管理员权限规则。

验收不要求跑赢某个模型，也不新增未经校准的分数门槛；要求报告完整、比较条件
明确、失败能解释，改进有同口径证据。保持旧结果不可变、使用独立数据库和结果目录，
后续改动可独立回退，不覆盖用户会话或历史实验。

## 7. 最脆弱的假设与扩围触发条件

目前假设本地合成任务加外部零售任务，足以暴露有价值的工程问题；若它们不能代表
实际客户表达，成绩只能说明这些受控条件下的表现。应补不同来源的经授权、脱敏、
已核实案例，保留事实未知与用户等待状态，而不是通过扩大合成数量宣称线上泛化。

先修实际复现的对象/否定/记忆错误；只有这条路线无法解决时，再评估额外语义审查、
更复杂任务队列或摘要。RAG 继续依据本店检索失败决定是否投入，当前 τ retail
不直接评价本店检索。τ³ banking_knowledge 是另一个领域和适配任务，暂不纳入。
