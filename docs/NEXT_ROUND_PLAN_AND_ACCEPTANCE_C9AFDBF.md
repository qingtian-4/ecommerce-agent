## 2. 审查发现：按修复优先级排列

### F1 / P0：取消草稿的后端授权判断仍接受间接否定

位置：`src/acs/sessions.py:318` 起的取消判断。当前规则寻找取消动作，只排除紧邻动作的少数否定词。

本次在临时数据库复现：已有草稿，当前用户说“我不是要取消退货草稿，只是问问。”，随后直接调用取消工具，结果为 `status=cancelled`、`order_id=null`。这是模型误调用时的后端防护缺口；不代表真实模型必然误调用，也不代表已提交申请可以被撤销。

建议以明确取消动作或可确认的取消流程收紧写入授权，测试否定、引用、假设、暂停和明确取消。不要仅追加几个正则就宣布自然语言授权问题解决。证据：[继承问题探针](../results/review_c9afdbf_20261021/inherited_probe.log)。

### F2 / P1：事实纠正发生在最终输出，流式阶段仍暴露错误

位置：`src/acs/chat_service.py:102` 的流循环与 `:112` 起的完成后纠正。

开启全部保护后，探针通过真实 Agent Loop 与 ChatService 注入错误模型文本：“您的订单一共买了25件商品。”。`running` 更新已包含该文本，随后最终答案和会话存储被正确改为“29 件商品”。所以最终结果检查通过，不能证明用户从未看到错误事实。

建议对受保护的事实段延迟展示，或直接用经过校验的结果生成展示；等待期间显示查询状态。验收应逐帧检查用户可见输出，并覆盖取消和异常中断。原始模型答案可留在诊断轨迹，不能作为已核验事实提前展示。证据：[流式复现](../results/review_c9afdbf_20261021/branch_probe.json)。本轮验证到服务更新层，未启动浏览器录像。

### F3 / P1：候选表与新统计模块的输入校验不一致

位置：`src/acs/order_candidates.py` 的 `order_lookup_result`；对比 `src/acs/order_reliability.py` 的 `_complete`。

基础候选表校验了嵌套字段类型，但未统一检查 `error`／`error_type`、`count` 与实际条数、重复订单及明细。探针分别注入错误包络、错误 count、重复订单，三种输入均被渲染成确定性候选表；新统计路径已经有更严格的检查。

这是协议防御缺口：当前正常 SQLite 工具输出未被证明会产生这些异常。建议共享一处最小的完整性校验，异常时明确查询不完整，不输出貌似可靠的完整表或统计。不要通过放宽新模块校验来统一行为。证据：[协议探针](../results/review_c9afdbf_20261021/branch_probe.json)。

### F4 / P1：查询与预览的规则来源及日期边界仍不一致

位置：`src/acs/database.py:178` 起；对照 `src/acs/returns.py` 的政策读取与预览计算。

- 临时政策副本将正文和表格期限一致改为 10 天，签收 8 天：订单查询仍返回 7 天窗口、判定超期，预览却允许继续。
- 签收日期为明天：查询返回 `delivered_days_ago=-1` 且 `within_return_window=true`，预览拒绝。

这是本轮在该分支重新复现的继承问题。建议让查询、预览与提交共用期限和日期边界规则，并验证政策变更使旧预览失效。10 天仅为诊断输入，不建议改变当前业务政策。证据：[规则探针](../results/review_c9afdbf_20261021/inherited_probe.log)。

### F5 / P1：评分诊断与业务成绩仍需分开

`task_eval.py` 相对上次审查的 main 没有变化；`raw_response` 在 JSON 解析成功后才赋值，解析失败不能保留原始文本，异常记录主要保留异常类型。应保存原始裁判文本、结构校验失败原因及评分器版本，明确区分“未判定”和“业务失败”。

上一轮已识别的历史校准案例仍应纳入修复：`boundary-10` 的本人跨会话申请与他人申请混淆，`confirmation-10` 的 `no_preview` 描述与实际成功预览轨迹冲突。这里只沿用已核对的历史案例并确认相关源码未变；本轮没有再次在线评分，也没有将旧模型成绩当作 c9afdbf 成绩。历史证据入口：[多轮评测记录](../results/iteration_v2_recovery/local_after/raw.jsonl)。

### F6 / 覆盖限制：固定句式和保守回退不等于通用理解

同一脚本模型漏存草稿时，“我想退S20017。”能触发补存，“请帮我退S20017。”不能。已设置白色耳机约束后插入“谢谢”，约束状态变为 `uncertain`，后续耳机请求不再恢复确定性颜色保护。这与当前保守设计一致，不应误报为违反已承诺范围的回归，但会影响自然对话演示。

下一轮先明确支持的用户流程，增加少量语义成对案例，测量“保护命中率”和“业务正确率”。需要扩大支持范围时，再考虑可验证的结构化查询／约束表示；不能以持续追加句式替代能力设计。普通闲聊是否保留偏好、无法理解的条件如何提示，应有明确交互约定。

## 3. 现有证据能支持什么

### 最新离线实现证据

[reliability_v1_offline 报告](../results/reliability_v1_offline/REPORT.md)包含 34 个冻结案例，每臂 3 次，共 204 段脚本模型对话。本轮核对了原始记录数及 manifest 中 9 个文件的 SHA256，全部匹配。

| 模式 | 开关关闭 | 开关开启 | 正确解释 |
| --- | ---: | ---: | --- |
| 颜色候选合同 | 0/21 | 21/21 | 注入错误输出时，限定请求被确定性纠正 |
| 统计合同 | 0/30 | 30/30 | 限定统计请求被正确计算 |
| 回退合同 | 51/51 | 51/51 | 保留原模型回答；其中可以包含已知错误 |
| 合计 | 51/102 | 102/102 | 工程合同通过数，不能写成业务成功率 100% |

这些结果支持“有限条件下纠正输出且不额外调用模型”。脚本模型的 token 不是实测模型消耗；新增类别元数据还会增加部分输入长度，不能据此宣称节省 token。已见案例属于开发／回归证据。

### 较早的在线证据

[p1_live_20261021 报告](../results/p1_live_20261021/REPORT.md)为 8 个任务、两臂各一次，共 16 段对话；两臂任务通过均为 5/8，事实通过均为 6/8。费用估算为 0.05106976 元，不是账单。

该实验发生在最新颜色约束与统计实现之前，不能用于证明这两个新功能的在线效果。白色候选案例中，开启侧原始模型回答本来就正确，不能把最终表格正确全部归因于保护。颜色限制当时仍存在于模型输入，不能把失败笼统解释为“历史被裁剪”。错误附带说明等回退案例也仍需如实展示。

### 推荐执行顺序与停止条件

1. 先冻结 F1–F5 的复现及预期；修复 N1，再处理 N2–N4。保留本分支已通过的草稿补存和事实保护测试，避免重复开发。
2. N5 在 N6 前完成。对固定历史答案重评分时保留旧分数与评分版本，分数变化属于测量修正，不计作 Agent 能力提升。
3. 明确 N6 的保护范围并冻结小批任务：原始失败、同义改写、插问／恢复／取消约束、数量与状态范围、协议异常、正确答案保持。已见原始失败和未用于开发的案例分别汇报。不得看完结果后删掉失败任务。
4. 建议从 12 个真实用户任务、每臂 3 次开始（共 72 段对话，不等于 72 个模型请求）。执行前固定确切任务、模型参数、开关组合、数据 hash、最大请求数、费用上限及停止条件；此处是规划，本轮未调用真实模型。
5. N6 至少记录：任务／事实通过数、保护命中率、误覆盖数、流式错误暴露、草稿误写／误清空、未判定数、请求数、真实 usage、p50/p95 耗时及可定价费用。样本小就报告绝对数，不以微小百分比差异宣称稳定收益。
6. 进入展示版本的门槛：目标离线反例全部通过，保护范围内不出现错误可见帧和错误写入；真实对照能解释逐例变化，不能出现尚未解释的关键退化。没有观察到原始失败的样本，只能说明该次未复现，不能证明修复有效。
7. 达到门槛后完成 N7 即停止本轮。未达到时保持保护功能的实验标识，记录失败及下一步，不为提高分数扩大范围或改判据。

### 架构与展示建议

本次源码没有显示必须替换自研 Agent Loop 的证据。先把业务事实、展示和评分的职责边界理清，并保留预算、工具协议、持久化与可观测性。后续确实需要跨请求长时间暂停、图式分支或人工节点恢复时，再按这些需求评估 LangGraph；迁移框架本身不能解决错误事实或评分误判。

React／FastAPI 也不作为本轮验收项。只有准备独立部署前后端、提供稳定 API 或改善当前交互已经受限时再拆分。作为实习展示，更有说服力的是约五分钟的可复现实例：查订单 → 确认商品与约束 → 补齐退货条件 → 预览与明确确认 → 管理员审核 → 查询结果，并展示旧预览失效或重复提交保护。审核通过仅表示允许退回，不等于退款到账。

复盘材料精选三条主线：模型改写业务事实、状态与写操作授权、评测误判及测量修正。每条给出失败轨迹、最小改动、对照结果和适用边界。
