## 1. 建议做成什么

做一个面向单店的电商客服应用：客户能咨询商品、定位订单、办理售后；办理信息能跨
刷新和重启恢复；需要确认的操作经过确认；需要核实的申请进入审核；最终结果真实可查。
项目的重点是自然语言理解与可靠业务执行之间的衔接。

核心演示流程为：

> 描述需求或定位订单 → 澄清与补信息 → 核对当前事实与政策 → 预览确认 →
> 创建申请 → 管理员审核 → 客户查询结果；中途更正、暂停、刷新或故障仍保持正确状态。

先交付单进程、合成业务数据、可容器运行的完整应用。生产工程能力用明确的运行边界、
角色约束、事务、预算、故障注入和可复核指标证明。当前不建设真实支付、仓库、跨店
平台、直播式人工聊天、向量数据库集群或多 Agent 系统。后训练需要独立证据与数据，
不在本轮路线中。

最脆弱的假设是“合成任务可以代表真实客服难点”。通过实际使用产生的失败、不同
任务组合的留出集和外部原版环境来检验；证据仍不足时，成果只表述为这些条件下的
表现，不宣称线上泛化或生产稳定性。

## 2. 这次会话揭示的实际问题

用户指定会话的最后一轮在北京时间 2026-10-15 00:18；推荐问题本身在 00:05。
数据库保存了完整对话，以下使用匿名化摘要，不复制原始会话标识或其他个人信息。

| 观察 | 根因或边界 | 下一步验收 |
| --- | --- | --- |
| 要求非入耳的挂耳款，后补预算 500；首轮检索 4 次，再查询 P001 | 没有提供完整商品目录给 Agent，知识检索被当成商品枚举 | 目录查询能得到全部耳机；硬条件不满足时明确无匹配，不硬推不合适款 |
| 回复只查到一款耳机，多轮继续沿用 | 数据库实际有 P001 入耳式与 P002 头戴式两款；命中片段不是完整目录 | 区分“没有满足条件的商品”和“店内只有一个型号”；头戴不等于挂耳 |
| 首轮共 5 个工具调用、8 次记账 API 请求、15,361 token、约 11.07 秒 | 缺少目录入口，也没有为重复无结果检索提供停止依据 | 同条件比较正确性、调用与完整耗时；这条是单次观察，不能当 p95 |
| 颜色、图片缺失时如实说明 | 当前没有 SKU 颜色和商品图片事实；这是数据能力缺口 | 有数据时能正确展示，没有时不编造，不指向不存在的商品页面 |
| “转人工”先说帮用户转接，再要求点击页面入口 | 没有人工接管工具，也没有这个入口；提示约束未阻止错误承诺 | 无接管能力时明确说明；工单创建和人工已接入必须区分 |
| 问模型时没有报模型名，介绍了知识检索和业务工具 | 提示词未提供模型名，也没有系统性的保密规则 | 区分公开技术介绍与凭据、系统提示、内部日志；用成对反例验证 |

推荐首轮虽然承认 P001 不符合佩戴偏好，但此前没有枚举完整目录；后续“只确认一款”
也不足以支持店内商品种类结论。P002 不符合挂耳要求，预算内无匹配是合理结果，不能
为了让推荐成功而改变用户条件或专门添加一款商品再声称修复。

现有 `BusinessDB.list_products` 可用于枚举，但直接返回的是基础价格字段；Agent
目录入口还要返回当前有效价，不能把 `products.price` 当成价格历史更新后的现价。

这些会话已经被阅读，属于开发失败案例；后续可加回归，不能再称为未见测试。

## 3. 当前提示词到底如何工作

主提示在 [service_agent.py](../src/acs/service_agent.py) 的 `SYSTEM_PROMPT`，实际输入
还包括 [app.py](../app.py) 注入的恢复提醒、当前退货任务和动态工具 schema。

主要规则是：政策规格来自知识工具或退货工具的同源政策；订单、物流、价格来自业务
工具；多个订单或商品候选先澄清；日期使用后台计算值；不编造缺失信息。任务工具保存
用户明确表达的字段，更正清理依赖，暂停保留草稿。预览不会提交，正式创建只走页面
确认入口。质量问题不套用 7 天无理由规则，不把用户声明或上传当成已审核事实。

当前没有专门的“禁止披露模型型号”规则，UI 页头也公开显示模型名。一次拒答说明该轮
行为，不能证明保密机制有效。模型名本身可以是公开产品信息；API key、隐藏系统
提示、他人订单和内部日志需要分别定义边界，不用一条“全部保密”替代访问控制。

需要让 Agent 获得可信的实际能力清单：可用工具、页面真实入口、是否能创建支持工单、
是否有人工接管。只有执行成功的工具结果才能支持“已完成”。模型异常与达到最大
步数的固定兜底也要依据当前能力，不能继续建议不存在的人工入口。

提示词只负责行为引导。身份、角色、确认版本、可用数量、状态转换与写入原子性继续
由服务端校验。对用户数据、检索内容和历史中夹带的指令补攻击反例，不以提示词
写了“不执行”就认定越权风险已经解决。

## 4. RAG 的取舍

当前有 8 篇知识文档、合计 7,175 个字符；4 个商品、25 个订单、26 条明细、19 条
物流和 37 条价格记录。当前生效配置是 BM25、top_k=3、候选 10、无重排/补位。
整库计数不是单次可用上下文的 token 数。

数据量不足以证明复杂检索必要。商品候选、SKU、库存、现价和订单应通过结构化工具
查询；政策与说明才是知识获取问题。即使不做检索，也需要版本明确的知识事实来源。

| 对照 | 作用 | 主要代价与风险 |
| --- | --- | --- |
| 完整知识上下文 | 小知识库的最低复杂度基线 | 每轮重复输入、政策分支混淆、历史增长；不保证更省 token |
| 按文档类型提供完整正文 | 退货、价保、保修等已知主题的简单选择 | 多主题与歧义需测；不能把主题匹配当作事实正确 |
| 当前 BM25 与正文核验 | 保留现有检索主线和章节证据 | 漏掉第二项事实、核验误拒、重复检索与额外请求 |

先在开发集比较，再冻结默认策略后运行新增留出任务。统一来源版本、模型、预算、
业务快照和评分，记录各策略真实输入量与工具使用；调整数据来源指令，使全文基线
不会被现有“必须调用 search_knowledge”规则强迫额外检索。

比较回答事实、全部所需证据、错误拒答、首段正文耗时、整轮耗时、调用、token 与成本。
质量接近时选更简单或实测成本更低的策略；已有 Dense/RRF/reranker 保留为实验选项。
检索组合继续投入的触发条件是明确的漏召回或排序失败，不是知识篇数目标或简历词汇。
独立 query rewrite 先收集指代失败，证明简单利用任务字段仍失败后再加入。

## 5. 两个评测项目能借鉴什么

阅读固定版本：τ 仓库 `dd8757d4c8791dad7b3cdaf02a105a3d5f9d86bd`；
ECom-Bench `bc5018daaf45eea12330941bce68cebd293cfa85`。τ 主分支 README 当前已经介绍
τ³；使用用户提供的仓库不等于运行原始 τ² 论文版本。后续报告必须固定版本与任务。

τ 的零售等默认评分关注数据库终态与要求传达的信息，参考工具轨迹用于构造目标状态，
通常不要求 Agent 逐个复制该轨迹。相同任务重复运行并统计持续成功，比挑一次成功
更能体现可靠性。参考：[评分定义](https://github.com/sierra-research/tau2-bench/blob/dd8757d4c8791dad7b3cdaf02a105a3d5f9d86bd/docs/evaluation.md)、
[终态实现](https://github.com/sierra-research/tau2-bench/blob/dd8757d4c8791dad7b3cdaf02a105a3d5f9d86bd/src/tau2/evaluator/evaluator_env.py)、
[重复成功指标](https://github.com/sierra-research/tau2-bench/blob/dd8757d4c8791dad7b3cdaf02a105a3d5f9d86bd/src/tau2/metrics/agent_metrics.py)。

ECom-Bench 更贴近中文电商，任务包含用户画像和多个连续意图，例如查教程、催物流、
查另一笔订单并要求取消。其实现比较预期动作后的数据状态，查询检查要求的函数参数
集合，输出检查字符串，时间单独统计。借鉴任务组合和维度拆分，仍需审计判据。
查询集合包含关系不能证明没有多查，字符串出现也不能穷尽语义或否定错误；该版本
最终 reward 未乘入时间分数。参考：[任务](https://github.com/XiaoduoAILab/ECom-Bench/blob/bc5018daaf45eea12330941bce68cebd293cfa85/envs/story/tasks.py)、
[环境与评分](https://github.com/XiaoduoAILab/ECom-Bench/blob/bc5018daaf45eea12330941bce68cebd293cfa85/envs/story/env.py)。

仿真基准不等同于生产后端。在这个 ECom 版本中，取消与退货工具直接改变状态，部分
前置条件写在提示词里；本项目仍需自己的权限、确认、数量与状态约束。
参考：[取消实现](https://github.com/XiaoduoAILab/ECom-Bench/blob/bc5018daaf45eea12330941bce68cebd293cfa85/agent/servers/offline/tools/manage_order.py)、
[退货实现](https://github.com/XiaoduoAILab/ECom-Bench/blob/bc5018daaf45eea12330941bce68cebd293cfa85/agent/servers/offline/tools/manage_return.py)。

优先把两者的任务方法落到本地。外部原版集成先选择 τ 的 retail 小子集：代理接口与
评分定义清晰，避免同时引入两套执行框架。ECom 用于中文多意图任务参考；原版适配
作为独立后续决策，不为接入基准强制迁移本地框架。

外部适配要复用本项目实际消息组织、模型调用和预算逻辑，接受原版领域政策、工具与
工具结果，由官方环境执行。不能只更换官方 Agent 的模型就报告本项目成绩，也不能
把本地按钮确认规则移入原版环境后继续称为原版。外部核心成绩和本地应用验收分开。

## 6. 成品的架构与界面

保留 Python、手写 loop、SQLite 与 Gradio。最低成本路线是暴露已有商品目录入口、
纠正能力声明、完成既定审核流程，并把 UI 回调里的对话协调提取成可直接评测的服务。
整个路线会涉及超过 8 个文件，按下面的独立交付切分；不新增分布式部署服务。

```text
客户界面 ─────┐
本地评测 ─────┼─> 对话服务 ─> Agent 核心 ─> 业务工具 / 知识提供
               │      │                         │
               │      └─> 会话与任务存储          ├─> SQLite 业务事实
               │                                └─> 版本化知识正文
确认入口 ──────┴─> 申请服务 ─> 校验 / 同事务写入 / 审计
受保护的审核入口 ─> 审核服务 ─> 合法状态转换 / 结果查询
请求与阶段统计 <──── 上述相同链路；评测读取真实状态与结果
```

建议边界：

- `app.py` 保留界面、展示与事件绑定；共同对话服务负责轮次、恢复、预算和结果保存。
  评测调用同一服务，逐步解除 `scripts/eval_return_submission.py` 直接依赖整个 UI。
  建议服务接口为 `ChatService.run_turn`，流式输出沿用当前 `AgentResult`；UI 只将结果
  转成组件更新。外部适配复用单步模型消息接口，不复制一个另有提示和预算的 Agent。
- Agent 核心负责消息与工具请求；领域政策、实际能力和工具 schema 从调用环境传入。
  运行宿主控制工具执行，外部基准适配可以接受官方工具结果，不访问本地售后库。
- 业务工具查询结构事实，申请/审核服务控制副作用；知识提供使用同一个版本来源。
  客户陈述、检索证据、当前业务事实、已执行结果分别保存。
- 第一版只支持单进程，最多 2 个不同会话的活动模型轮次；同会话继续拒绝并发。
  业务事务不等待外部模型。额外请求排队且可见，不宣称多实例支持。
- 建议整轮预算 120 秒，保留最多 6 个 Agent step；API 调用与重试均占预算。
  单次超时不得超过剩余整轮预算。只读重试与写后结果核查分开，断流不伪报成功。
- 首版模型输入按 24,000 字符预算保留完整近期轮次及当前任务，字符不称为 token。
  原始历史完整存储；裁剪不拆工具请求/返回。先用长对话测字段和指代，再决定摘要。

这些限额是建议的运行边界，须在实现时冻结并测试，不是实测容量或生产 SLA。

界面建议分为三个工作场景：

| 页面 | 主要内容 | 验收体验 |
| --- | --- | --- |
| 客户服务 | 对话、商品候选、本人订单、办理摘要、预览确认、申请状态 | 客户清楚下一步做什么；看不到工程 JSON；能力与实际入口一致 |
| 运营审核 | 待审核列表、订单事实、声明、原凭证、审核原因与记录 | 通过/拒绝后客户可查，已审核不能再次审核，无权限调用被拒绝 |
| 工程评测 | 轨迹、耗时、token、版本、失败分类、对照和回放 | 能解释每次失败发生在哪一层，历史回放与当前运行明确区分 |

不为界面观感重写 React 前端。先用现有 Gradio 做职责明确的展示；其安装版本支持
独立管理入口认证，不需要重建客户账户系统。客户页保留模拟身份；管理动作必须校验
可信角色。若管理入口启用，新增 `ACS_ADMIN_USERNAME` / `ACS_ADMIN_PASSWORD`，
仅用于管理入口，并由服务端把已验证账号映射为审核角色；对外服务还需接入真实
客户认证，模拟用户下拉框不能公开当认证使用。

“人工审核售后”与“人工接入聊天”不同。先做审核闭环；无实时接管能力时明确说明。
若后续加入支持工单，必须有持久工单号、队列状态、操作者和结果，客户看到的是
“已创建工单”，不能描述成“人工已接入”。实时人工聊天不作为这轮交付依赖。

## 7. 数据与评测怎样变得有说服力

### 数据

先补覆盖，不追求文档总数。建议在独立 v2 演示/评测库构造 12 个商品型号、约 24 个
SKU、60 笔订单，覆盖不同佩戴类型、价格段、颜色、可用/不可用，以及多明细、购买
数量大于 1、取消、未签收、窗口边界、已占用售后数量。保留真正无匹配的推荐条件。

商品候选从目录查询，可核实的颜色、库存与现价来自 SKU/价格数据；说明正文放入
知识来源。缺失字段保持未知。数据采用明确标注的合成规格，不伪装为品牌官方产品
资料。图片有合法来源才添加；演示示意图标明用途，不把占位图描述成实物图。
SKU 最小字段为商品/明细标识、佩戴类型、是否支持主动降噪、颜色、可用状态；
有效价格继续由价格记录推导，明确未知字段，不让模型从营销描述猜出结构事实。

新数据不覆盖当前 `business.db` 或旧评测快照。时间、种子、政策、知识与数据版本
一起记录；迁移保留原历史和申请。小目录的失败先在原事实下修复，扩展数据的效果
另测，避免用换数据冒充 Agent 改进。

### 本地任务评测

建议建立 80 段场景：40 段开发、40 段新增冻结留出，每段 4–12 轮。八类场景各 10 段，
各一半开发、一半留出：

1. 多条件商品咨询与无匹配，包含预算、佩戴方式、颜色、信息缺失。
2. 模糊订单定位、多商品与澄清。
3. 无理由申请、数量与资格边界。
4. 质量问题、声明与凭证缺失。
5. 闲聊后继续、更正、暂停、中止与长历史。
6. 预览确认、政策变化、提交响应丢失与重复操作。
7. 审核与查询，以及跨用户、跨角色访问。
8. 无法处理、人工能力、虚假操作承诺及用户/知识中的恶意指令。

留出应使用不同任务组合与措辞，不只替换订单号。先冻结任务、预期事实和业务快照，
再运行；已看过的真实会话和公开验证一律归开发。作者知道语料，仍不能称为严格盲测。

以脚本用户验证确定的状态与失败边界，再用真实模型做多轮任务；模拟用户有独立角色，
不能看到评分答案。页面确认与上传在应用评测中显式执行真实处理器，不能由模型文本
假扮按钮或凭证。审核操作由测试中的可信审核身份执行，属于完整应用的参与方。

成功必须同时满足业务终态、必需信息传达与禁止副作用约束。只看没有写单，不能证明
一次本该成功的申请完成；只看行数，也不能发现把质量规则解释成 7 天的问题。
本地比较订单、明细、数量、状态、角色与引用关系，随机 UUID/时间使用关系校验，
不因它们不同误判，也不忽略其他用户是否被修改。

| 指标 | 定义与用途 |
| --- | --- |
| 任务完成率 | 数据终态正确、必要回答事实正确、未发生禁止操作的任务比例 |
| 约束违规 | 未确认写入、越权、超量、非法审核与虚假完成承诺分别计数 |
| 记忆正确性 | 字段、更正、来源、指代及已知信息重复追问，逐轮标注 |
| 持续成功 | 留出每段独立运行 3 次，报告平均成功及三次均成功比例；不是至少成功一次 |
| 故障恢复 | 断流、中断、响应丢失、数据库故障后状态及下一步处理正确 |
| 交互与效率 | 首段正文与完整耗时、排队、调用、token、完整/部分成本、轮次数 |

状态与精确事实优先用确定判据，表达和政策关系用成对反例及逐条复核。若引入 LLM
裁判，先在人工标注样本上验证错误检出，记录裁判模型与成本，不把它作为权限或事务
判断的唯一依据。英语开场等表达问题保留为独立维度，不靠后处理掩盖原始回复。

建议交付门槛：新留出平均任务完成率至少 85%，三次均成功任务至少 75%；固定约束
与故障反例无禁止副作用。门槛是目标；即使达到，有限样本中的 0 次违规也不等于
线上绝不会违规。低于目标时发布实际结果和失败分类，不调整任务或判据以达标。

### 故障与部署

补充整轮预算、SDK 重试、限流、部分流、重复点击、竞争占用、提交后崩溃和审核竞争
等有根因的故障验证。沿用已有完整回归，不为了增加测试数量写重复测试。
容器验收包括持久目录、重启后查询、知识/索引版本检查、数据迁移、只读存活检查、
API 不可用时的真实失败和 2 个会话的受控并发。先从请求轨迹定位瓶颈，再决定数据库
或并发方案；目前不引入 Redis、消息队列或多个服务。

基准依赖兼容与模型连接在实施时验证，本次阅读不等于已验证可运行。

## 9. 目前可以讲的技术经验

| 已经有证据的经历 | 能解释的技术判断 | 不能扩大成的结论 |
| --- | --- | --- |
| 数据时间轴一致性修复 | 模型解释前，业务事实本身必须正确；种子与日期也需校验 | 模型回答准确率提高了同样幅度 |
| 12 个错误反例从漏检到拒绝 | 指标先证明能抓错误；答案与工具调用分开评分 | 评分器已能判断所有语义 |
| 历史配对实验调用 160→122、额外调用 43→5 | 工具的信息边界、必要证据与调用成本；减少调用曾导致质量回退 | 当前新版本整体精度、token 或延迟一定更好 |
| RRF 漏掉第二项事实，补位/重排分别验证 | 召回、排序、过滤、覆盖不是同一个问题；复杂方案有额外消耗 | 加 reranker 就优于简单基线 |
| 暂停误清空修复、持久任务与原话来源 | 历史、当前任务、实时业务事实分工；解释错误应被状态约束挡住 | 已具备通用长期记忆 |
| 确认、同事务写入、数量约束、幂等与响应丢失检查 | LLM 可以提议，执行授权和数据不变量由服务守住 | 已实现生产退款或真实身份认证 |
| 当前推荐与人工入口失败 | 检索未命中不是完整目录事实；自然语言说完成不代表执行完成 | 当前所有咨询都已经可靠 |

310 项测试、阶段 3 的 5 段状态检查和各阶段检索结果有不同验证范围，不能合成一个
总成功率。简历优先选 2–3 个能独立复现、解释失败与修复的故事，注明数据条件和代价。

代码是借助 AI 完成的，不自动等于掌握。每次交付后亲自完成一项复现：能定位调用、
查看输入与数据库、制造反例、解释为什么修复有效，并独立复算指标。能回答“如果
去掉这个校验会出现什么、为何选简单方案、失败后保存了什么、这个数字不能证明什么”，
才形成可用于面试的经验。
