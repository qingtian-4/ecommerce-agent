# 两周迭代：有记忆、可恢复的电商售后 Agent

需求基线：2026-10-12。范围修订：按用户要求取消客户登录，继续 Agent 任务记忆主线。

本文整理本轮已确认的范围，并根据当前代码核对实施细则。按阶段验收逐步交付，
以末尾的实施记录区分已完成与待实现。推进周期约两周，以每天共同开发、复现和讲解
一个可验证成果为节奏，不规定每日工时。
两周是安排目标，以完整可运行、测试通过和证据齐全为交付门槛，不按日期宣布功能完成。

## 1. 目标与交付范围

面向 Agent 应用开发实习，完成一条可以演示、部署、审计和验证的客服业务流程：

> 定位订单 → 补齐退货信息 → 查订单与政策 → 展示申请内容 → 用户确认 →
> 创建售后单 → 管理员审核 → 用户查询结果。

技术重点是会话与任务记忆、受控业务操作和异常恢复。保留现有商品、政策、订单、物流
与价保咨询能力；取消订单和价保申请作为后续计划。后训练与 LoRA 是后续方向。

本期退货粒度为订单明细与数量，每张申请对应一项订单明细。管理员审核通过表示允许
退回商品；本期业务终点是审核通过或拒绝及结果查询，仓库验收和退款到账不在本期范围。

沿用当前 Python、手写 Agent loop、Gradio、SQLite 和检索组件。对话使用现有 DeepSeek
配置，embedding 与 reranker 沿用 SiliconFlow。根据失败证据选择检索配置，保留当前
BM25 默认及其他对照模式，不通过增加框架或模型替代问题定位。

## 3. 记忆的产品行为

同一用户可从历史会话列表选择继续未完成的申请。刷新页面、切回模拟用户或服务重启后，
先展示当前任务摘要，再由用户选择继续。新会话不自动继承另一段对话的订单和申请。

记忆分三部分，使用 SQLite 持久保存：

| 内容 | 保存目的 | 使用规则 |
| --- | --- | --- |
| 对话记录 | 保留用户原话与可观测交互 | 对话按用户和会话隔离；业务权限仍由服务端校验 |
| 当前任务信息 | 订单、明细、数量、原因、用户自述、缺失信息 | 保存来源；已提供且未变更的信息不重复追问 |
| 办理进度 | 澄清、等待确认、已提交及对应售后单 | 提交结果以业务记录为准，不能由摘要推断操作成功 |

用户修订订单、商品、数量或原因时更新任务版本，使旧申请预览与确认失效。用户自述
与后台事实分别记录，例如“未拆封”首先是用户陈述，仍需审核；恢复任务和提交前重新
校验业务状态与政策，不能将历史窗口判断作为实时事实。

历史记录可完整保存，模型上下文按实际预算选择近期消息和当前任务信息。裁剪须保留
完整工具调用与结果配对。若需要摘要，保留可追溯的原文，订单、数量、确认与操作结果
以结构化记录为准。先测长对话失败，再决定是否需要额外摘要调用。

同一会话同时只允许一个进行中的请求，多窗口不能覆盖彼此的轮次。先保存用户请求，
完成后原子保存完整的模型消息组与回复；半截工具调用不作为已完成上下文。
服务重启后的未完成轮次标为中断，由用户重新发起，不能自动重放业务操作。
本期使用单进程应用；多实例共享数据库前须增加运行实例与存活判定，不能让一个实例
启动时终止另一个实例的有效请求。

对话恢复只是保留语境，不把旧工具返回作为当前事实。阶段 1 恢复后向模型提示重新
核查当前业务状态；阶段 3 的提交校验必须在后台读取当前订单与政策，不能依赖提示词。

## 4. 订单定位与退货办理

### 4.1 订单定位

将受当前用户权限限制的订单列表与明细查询能力提供给 Agent，支持“最近买的耳机”
等描述。多个候选时展示选项并澄清，不能猜一笔订单。后续“这单”“只退一个”等指代
必须关联到已选择的订单和商品；切换订单后清理失效的任务信息。
用户明确中止当前退货草稿时清理办理状态并使预览失效。这是中止草稿，不是取消订单。

### 4.2 申请与审核边界

- 必要信息包括订单、明细、数量、退货原因，以及政策要求的相关条件。
- 支持无理由退货与质量问题申请；自动校验权限、订单状态、数量与适用日期窗口，
  商品状况和质量问题真实性交由管理员审核。质量凭证缺失时应明确待补充，不能判为
  已核实或承诺审核通过。
- 根据现有政策“质量问题需上传照片或视频”，缺凭证时保留草稿并提示待补充，
  不提供可提交的质量退货确认。阶段 3 接收凭证及其来源，上传不等于审核已核实。
- 现有 `within_return_window` 仅是 7 天窗口，不代表完整资格。质量问题的 15 天规则
  来自知识库；后台校验规则须与知识政策同源并记录版本，不能让模型自定期限。
- 待审核和已通过申请占用对应退货数量；拒绝申请释放占用。累计占用数量不能超过
  购买数量。并发和重复请求也必须满足这一约束。
- 管理员可通过或拒绝申请，保存审核原因；状态变更与审核操作留有审计记录。
- 用户只能查看本人申请，管理员操作权限由服务端校验。模型不能决定调用者身份。

### 4.3 确认、幂等与恢复

生成申请预览不创建售后单。用户通过明确的确认入口授权当前申请版本；执行时校验
用户、申请内容、版本和授权有效性，并重新检查业务条件。模型首次调用申请工具不能
直接完成提交，普通聊天中的引用或含糊表达不能自动成为确认授权。

售后单创建、幂等结果、授权消费与审计写入使用同一事务。相同逻辑请求重试返回同一
售后单；响应丢失后先查提交结果，不直接创建新申请。修改内容后必须重新预览与确认。
已完成提交的结果应可查询，不能因授权已消费而丢失恢复入口。

管理员审核只能进行合法状态转换。售后审核队列可用于人工处理待核实申请；若后续
实现通用人工接管，需另行定义消息接管与恢复机制，不能仅改一句回复就宣称已转接。

## 5. 最小运行能力

- 客户页用模拟用户选择体验合成数据，暂不做客户登录；这不是账户认证。
  模型不能指定身份，数据层仍检查所选用户归属。阶段 4 的管理操作须单独校验角色；
  面向真实账户或对外部署时再确定认证接入，不把下拉模拟身份当成权限入口。
- 持久保存会话、任务、申请、确认记录和操作审计；保存可复核的请求轨迹、错误类型、
  停止原因与请求用量。按用户校验历史会话访问权限。
- 为模型请求、工具循环和整轮请求设置可解释的停止条件；对超时、限流、断流和无效
  参数分别验证行为。写操作是否可重试取决于已记录的业务结果。
- 提供本地和容器启动方式、状态检查与持久数据目录。基础部署验收在可控环境进行，
  对外发布单独决定。
- 对现有数据库使用非破坏式迁移。`scripts/init_db.py` 当前会重建业务表，不得用于
  正常升级已有会话与售后数据；测试和演示种子数据应有明确的重置入口。
- 如果政策数据或 embedding 输入改变知识指纹，重建索引、更新必要版本并复测相关性
  标定与检索回归，过期结果不能继续静默服务。

## 6. 可独立验收的交付顺序

| 阶段 | 可运行成果 | 主要验收 | 学习与复现任务 |
| --- | --- | --- | --- |
| 1：会话记忆 | 模拟用户、持久对话、历史选择、按所选用户校验归属，已有只读对话仍可用 | 刷新、用户切换与重启后恢复同一会话，越权加载失败 | 解释消息历史、会话身份与数据库持久化的关系 |
| 2：任务记忆与定位 | 当前申请信息持久化、订单候选澄清、用户更正 | 不重复追问已知字段，多商品指代正确，修订不串单 | 复现插入无关消息、切换订单和数量修订 |
| 3：受控退货申请 | 预览、确认、提交、数量约束、幂等与审计 | 未确认无售后单，旧确认无效，重复与并发不超量 | 复现提交成功但回复丢失，解释事务与幂等 |
| 4：审核与查询 | 管理员审核工作台、用户查结果 | 合法状态流转、审核原因留存、跨用户访问失败 | 解释模型决策与后台权限、状态约束的分工 |
| 5：异常与部署 | 持久轨迹、请求停止条件、容器运行和恢复 | 超时/限流/断流可见，重启不丢任务，已有查询回归 | 根据轨迹定位一次模型、一次工具和一次状态故障 |
| 6：评测与展示 | 当前版本端到端结果、对照与项目讲解材料 | 条件冻结、错误保留、指标可复算、演示可重现 | 独立讲清一个失败的根因、修复与指标变化 |

阶段按依赖推进，允许根据实际失败调整顺序，但调整时记录原因。每阶段包含实现、
必要回归、相关文档与证据，保持完整可运行的交付。现有 `.gitignore` 和
`skills-lock.json` 是用户工作，本轮不修改或混入实现提交。

每个阶段先冻结自己的验收用例与条件，再做基线和改进对照；阶段 6 负责整条流程的
集成评测、重复运行与讲解材料，不把前五阶段的验证推迟到最后。评测中的本地持久
会话与在线模型回答分别检查，恢复消息完整不能直接表述为模型任务成功率提升。

当前身份由页面的模拟用户选择传入，只允许已有合成用户。切换会清空界面上下文；
SQLite 的创建、列表、加载与写入仍按用户和会话校验，不依靠模型约束归属。
保留阶段 1 的 `acs_migrations`、`conversations` 与 `conversation_turns`；阶段 2 v2
迁移追加 `return_tasks`，所有草稿写入必须绑定当前进行中的会话轮次。
取消原客户登录模块、账户配置项和生成脚本，不删除原会话或修改本机凭据文件。

## 7. 本地验收与指标

先冻结新增用例，再运行当前基线与改进版本。事实从业务数据库与知识库推导，保留
有效但检索失败的问题；不通过筛选问题或放宽判据提高成绩。

### 7.1 必须有回归的行为

1. 同会话已提供订单、商品、数量或原因，后续不再追问相同字段。
2. 插入多轮其他咨询后继续退货，任务信息仍正确；新增相关事实正确更新。
3. 刷新、切换模拟用户或重启后，可选择同一会话并恢复未完成任务。
4. 明确切换订单、商品、数量或原因后，以新内容为准；旧确认不能提交。
5. 模糊订单描述存在多个候选时澄清，不擅自替用户选择。
6. 无理由与质量问题按各自日期窗口校验，覆盖窗口边界与第 8–15 天的质量申请。
7. 用户未确认、确认过期或内容不匹配时，不创建售后单或成功提交审计；失败轨迹可记录。
8. 重复提交、两个并发提交及提交成功但回复丢失后重试，售后数量和单据保持正确。
9. 数量非正数、超过购买数量或超出剩余可申请数量时，后台拒绝。
10. 用户无法读取、恢复或修改他人的会话与申请；普通用户无法审核。
11. 管理员审核与用户状态查询使用业务记录，拒绝时给出真实原因。
12. 模型超时、限流、断流、非法工具参数及最大步数停止可见，失败不宣称操作成功。

### 7.2 指标分开报告

| 维度 | 衡量内容 |
| --- | --- |
| 业务结果 | 申请内容、数量、审核终态与数据库副作用是否正确 |
| 记忆行为 | 任务字段正确性、更正是否生效、重复追问已知字段次数 |
| 恢复能力 | 重启后任务恢复、提交结果核查和幂等重试是否正确 |
| 检索与回答 | 所需事实的证据覆盖、答案事实与未实现操作的错误承诺 |
| 执行约束 | 权限、用户确认、禁止副作用、数量与状态约束是否满足 |
| 效率与稳定性 | 实际请求链路调用、token、部分成本、耗时分位数与重复运行变化 |

重复追问指标需根据当轮用户输入与已有任务状态标注，不能仅依靠问号或关键词判断。
修复已有规则误判时先保留成对正反例，并明确区分测量修正与业务能力提升。
离线测试验证结构性约束；真实模型行为需要另做在线评测。未定价的 embedding 或
reranker 消耗标明成本不完整，单遍成绩不宣称稳定性。

## 8. 外部评测与简历证据

本地完整流程与异常用例是必做项。外部原版子集是附加成果，最多安排约两天适配；
在本地流程完成后，根据能力覆盖选择一个基准，提前固定版本、任务 ID、筛选规则、
模型角色与重复次数，不按已看到的成绩选择题目。

- 原版子集使用原版环境、工具、政策和评分方式，接入本项目实际 Agent 流程，单独
  报告子集成绩与覆盖范围。不能只将官方 Agent 的模型换成 DeepSeek 就称为本项目成绩。
- 替换成本地数据、工具或政策的用例标为改编评测，不与官方榜单直接比较。
- 当前 `tau2-bench` 主分支已演进到 τ³，部分任务使用额外语义裁判；裁判配置与版本
  必须单独记录。ECom-Bench 的中文任务与业务更接近，但需要额外工具与轨迹适配。
- 不把外部工具环境下的成绩当作本地知识库检索或整个应用部署的验证。

最终保留：可运行代码、迁移与启动说明、代表性正常/异常演示、冻结评测条件与原始
结果、失败分类、同条件对照，以及 `docs/PROBLEM_SOLVING.md` 中的根因和量化结论。
简历只使用实际实现与实测数字；访谈中的目标和历史旧成绩不作为当前成果。
