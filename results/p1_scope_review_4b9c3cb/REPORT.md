## Standards

独立规范审查（实际 diff 与源码，非仅阅读历史报告）：

- **P1：缺少用户诉求边界。** `src/acs/order_candidates.py:19–30` 无用户文本，
  `src/acs/chat_service.py:112–116` 直接整体替换。与 AGENTS.md 的最小范围、业务事实
  正确且完成任务的要求不符。原探针对正确短答也断言 25 行，遗漏任务完成度。
- **P2：嵌套展示协议校验不足。** `order_candidates.py:35–45` 对缺失 ID、非字典订单、
  非法 items/SKU 直接索引或调用 get；未验证即可转为回答。不是实际 SQL 数据常态的证据，
  是边界注入发现。
- **P2：缺失明细生成占位事实行。** `order_candidates.py:39` 的 `or [{}]` 将缺失/空
  items 转为一条未知明细；应放弃接管，不能用虚构明细补齐协议。

三个发现，规范轴最高 P1。已有转义、对象绑定和终态同步可复用；没有重构理由。

## Spec

独立需求审查：

- **P1：整体替换破坏筛选、统计与短答。** “只列白色”“只列已签收”“共几单”
  都满足现有代码入口，却被替换成 20 单、25 明细全表。满足新需求的事实精度不足以
  抵消任务失败；正反例见下表。
- **P1：异常数据不能安全放弃接管。** helper 抛错后 ChatService 无局部处理，
  `finally/interrupt_turn` 将正常生成结束的回答记录为中断。数据缺失也会生成未知行。

两个发现，需求轴最高 P1。实际 list_orders 按应用身份读取，来源为同轮工具结果；
answer、assistant、final Trace、会话保存同步，无新增模型或业务写入。两轴保留各自严重度。

## 冻结与口径

冻结输入：[order_candidate_scope_v1.json](../../data/eval/order_candidate_scope_v1.json)，

独立 detached 工作树固定 4b9c3cb，合成场景数据库每臂复制，禁用 socket 网络。
每段固定 list_orders → 固定模型回答 → 固定下一轮回答，非真实模型成功率评价。

事实指标独立读取最终 Markdown 行中的订单、明细、商品、SKU、颜色、数量、状态、日期，
与数据库快照比较；不信任 fact_render 自报正确。行是复合事实单位，不是每字段计分。
明示订单/商品总数与颜色短句另作事实声明。没提事实记未判定，不当成正确。
任务完成要求精确对象集合，退货候选需追问确认；统计要求正确单位且不铺列表；
短答不超过 100 字且只涉及指定订单。单次输出任务失败不推断模型失败概率。
校准包括空答、错色、缺行、错误计数和“事实全对但含无关行”，见
[评分校准](baseline/calibration.json)。

“覆盖正确答案”=文本变化；“有害覆盖”=原回答正确且完成任务，替换后失败。
数量统计的全部订单都与计数有关，故无关订单为 0；但多出 25 行是格式/任务失败，
另记 unwanted_rows，避免为夸大缺陷混淆两种指标。
原始 orders-01 仅审计原文显式合并的 S20008/S20003 两个颜色声明，1/2 正确；
表格为全行审计，不与主 14 段混合平均。“最近”未提供时间界限，不能称此处已验证完整语义。

## 最小设计决策

先交付本分析和可复现实验，再做局部修改；本阶段无生产代码变化。

1. **允许的唯一小修：展示协议校验。** 全批次先验证订单和明细为字典、必需标识为
   非空字符串/正整数、quantity 为正整数（拒绝 bool）、items 为非空列表、SKU 为 null
   或带标识及标量颜色的字典；日期/状态为字符串或 null。任一项无效返回 None，
   继续原模型正常终态。缺失 items 不生成 [{}]。合法空订单列表和未知 SKU 保留。
   不增加 SQL、异常重试或工具调用，不修改 ChatService/ReturnService/P0。
2. **净收益闸门。** 必要性由 7 次中断与 5 次不合规接管证明。结构校验不会筛选或
   改写任何合法行；验证后必须实测全部合法回放答案、五项指标及上下文逐项保持一致，
   异常安全放弃从 0/12 到 12/12，且业务快照不变，才接受此小修。未通过则不提交修复。
3. **暂不实施意图路由。** 仅允许“全部订单+明细”的关键词白名单虽可避免主矩阵的
   11 个覆盖，却会令原始“退最近买的耳机”退回已知错误颜色。不能拿任务分上升换掉
   已有事实收益。类别在当前 compact list_orders 中没有独立类别字段；筛选、最近时间
   和计数需要先确定有据可查的展示契约，不能按本次字面题目拼路由。

未来可考虑接管的边界是显式全量、无条件订单明细列表，以及显式全量退货候选澄清。
禁止接管的边界是类别/颜色/状态/时间/指定订单筛选、统计、短答、混合请求、已有任务、
工具错误或不合规数据。**目前代码没有实现这条语义边界，不能把建议写成已生效限制。**

因此即使结构校验通过，仍不建议将当前 P1 作为完成的接管方案合并，更不能默认开启。
若只保留默认关闭代码作实验，应单独明确接受尚未修复的语义路由风险，不属于本次验收通过。

### 接管建议与剩余风险

| 问法 | 建议 | 当前实现 |
| --- | --- | --- |
| “请列出我的全部订单和全部商品明细” | 可作为无筛选全量展示入口候选 | 可以接管，主矩阵此例成功 |
| “退货前请列出全部订单和明细让我选择” | 可作为全量候选澄清入口候选，仍需用户确认 | 可以接管，此例成功；不办理业务 |
| “只列耳机/充电配件”“只看白色”“排除白色” | 不能接管 | 仍错误接管为全表 |
| “只列已发货未签收/已签收”“只看 S20008/S20003” | 不能接管 | 仍错误接管为全表 |
| “多少笔/多少件，只给数量”“一句话告诉我 S20008 颜色” | 不能接管 | 仍错误接管为全表 |
| “最近”、时间界限、混合条件或资格/政策请求 | 不能按当前协议接管 | 单次 list_orders 时仍可能接管；无已证实语义保障 |
| 已有任务、工具错误/混合工具、状态不可读、非法展示数据 | 不能接管 | 既有入口限制或本次新增结构校验拒绝 |

以上“可作为候选”是未来入口边界，不是一个已经实现的语义路由。
**最终结论：P1 暂不建议合并，不能默认开启；可交付这次独立的结构安全修复。**
下一轮最具体的 Badcase 是 short-colour：正确短答被全表替换，带入 19 个无关订单，
下一轮输入 +1975 字符。先明确用户请求范围与输出形式，再同时保住原始 orders-01
颜色纠错；不得用白名单把原始缺陷放回去。冻结例均已见结果，后续只能作开发/回归。
